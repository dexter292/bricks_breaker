<objective>
Wire endless mode into the host: intercept the win, generate the next board, swap it in, count
the wave, record the run through the existing funnel, and put a temporary `__DEV__` entry on
the HUD so the mode is playable before Phase 14.

Purpose: this is where the phase becomes a thing a person can play. It is also where the real
SC-5 risk lives — not in generation, but in the glow-bake and audio-preload cold path that
currently re-fires whenever the bake key moves.

Output: endless run state, the WON intercept, the endless record write, the bake-key fix, the
`__DEV__` entry, and the source-contract tests that pin all of it.

## Decisions made here, not deferred to the executor

**D-08: generation is lazy, at the transition.** `generate` plus `loadAndCompile` measured
0.0362 ms in Node and roughly 0.56 ms Hermes-scaled — about 3 % of a 60 Hz frame — and it runs
on the RN JS thread inside a `runOnJS`'d callback, where it cannot preempt the UI runtime's
frame callback at all. Eager pre-generation during wave N buys nothing measurable, adds a
cache to invalidate and adds a second code path Phase 12 would have to reason about.

**D-10: endless is host-local state, entered by the `__DEV__` button. No new prop, no
`GameHost` change.** D-05 places the entry "alongside the existing Lv / Auto high / Cert WC /
Crash dev buttons on the HUD", which is inside `PlayingHost` already. Threading a `mode` prop
down from `GameHost` would build shell plumbing that CONTEXT explicitly defers to Phase 14 and
that Phase 14 would then have to replace. Keeping the mode in `PlayingHost` state means Phase
14 deletes one button and adds one prop, rather than unpicking a half-built shell.

**D-13: the wave number renders in the `__DEV__` dev row, next to the entry button.** The mode
itself is `__DEV__`-only this phase, so a production HUD slot would be chrome for a screen no
player can reach — and production shell chrome is Phase 14's scope by CONTEXT's own boundary.
Rendering `W{n}` in the dev row also keeps `src/runtime/GameScreen.tsx` untouched, which keeps
the render-layer path-contract tests out of this phase's blast radius. `docs/ops/ENDLESS-MODE.md`
records that the production placement is a Phase 14 decision.

**D-14: the bake key is re-keyed on brick dimensions alone.** `loadKey` currently embeds the
level id and `compiled.brickCount` (`PlayingHost.tsx:289-290`), and the brick count moves every
wave as difficulty ramps — 32 bricks at d=0 to 128 at d=20. A naive wave swap therefore flips
`fxReady` false and re-runs `setActiveRef.current(false)` → `bakeGlowSprites` → `setBakedKey`
→ an awaited audio preload with a 2500 ms timeout (`:426-470`). That is a multi-hundred-
millisecond stall, three orders of magnitude worse than the 0.56 ms everyone was watching, and
it is the actual SC-5 risk. `bakeGlowSprites(brickW, brickH)` depends on nothing but those two
numbers (`src/render/textures/bakeGlowSprites.ts:95-108`), and every generated board uses the
one fixed lattice (`brickW: 32, brickH: 14`, `src/levelgen/grid.ts:32-41`), so a
dimension-keyed bake fires exactly once per endless run. It is also a strict improvement for
campaign, where two levels with the same brick size currently re-bake an identical atlas.
</objective>
