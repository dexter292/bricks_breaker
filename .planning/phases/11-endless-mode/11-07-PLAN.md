<objective>
Close **gap 1** from `11-VERIFICATION.md` (`status: failed`): the two pre-existing
run-boundary resets in `PlayingHost` were written for campaign, where "reset the world and
the counters" *is* a new run. In endless a run additionally owns a seed, a wave number, a
mode and an in-flight advance guard, and neither `onRetry` (895-920) nor `remountDevSession`
(1014-1038) touches any of them. The consequence is durable: an endless Retry resumes on the
wave-N generated board with three fresh lives, and the next loss records wave N+1 through
`mergeEndlessRecord` into AsyncStorage. `bestWave` therefore measures "deepest wave reached
across a chain of free resumes", which no single run produced.

Purpose: make the run boundary mode-aware so the phase goal's own words — *a record worth
chasing* — are true of the number that gets persisted.

Output: a mode-aware `onRetry` / `remountDevSession`, a single in-flight-abandon funnel, a
terminal wave-build-failure path that releases the advance guard, and the behaviour test that
no existing test provides (`11-VERIFICATION.md`: *no test drives Retry in endless at all*).

**Out of scope, deliberately:** a production endless entry point (Phase 14, recorded
`deferred` not `gap`), and SC-5's device frame reading, which stays the standing
human-verification item in `.planning/STATE.md` § Pending Todos and
`docs/ops/ENDLESS-MODE.md` § Limits item 2. No task here pretends to close SC-5.

**A-01 — `startEndlessRun()` failing to build wave 1 from Retry** (11-UI-SPEC § UI

`checkpoint:decision` in Task 3 rather than picked at planning time. The owner answered on

Results overlay stays on screen, its body copy is replaced with

> `Wave 1 could not be built — tap Retry`

and `Retry` stays live so a second press re-mints a different seed. The em-dash is U+2014,
matching the mid-run body `Wave {n} could not be built — run saved`. The literal `Wave 1` is
contract copy and **must not be templated** — a Retry-time failure is always at wave 1.

would tell the player `run saved` at a moment when there is no in-flight run to save — the exact
false claim the UI-SPEC flagged the row for; `silent-noop` would leave a dead-looking Retry
button, the failure shape 11-VERIFICATION called out for `LevelErrorOverlay`, and would break the
E2 `loading` contract that Retry is always live once the overlay renders.

Implemented by Task 4 step 4. The string becomes contract copy consumed by plan 11-08 and is
recorded in 11-UI-SPEC § Endless copy and § UI Considerations E2 `error`.

**A-02 — the other `__DEV__` row controls after endless is entered** (11-UI-SPEC § UI
Considerations E5 `error`, `⚠ unresolved`; `11-VERIFICATION.md` WR-02). `modeRef` is written
only to `'endless'` (1061), never back to `'campaign'`, so the compiled-push gate effect

control behaviour itself is left open for the owner.

**A-03 — the per-run seed can collide inside one millisecond.**
`runSeedRef.current = Date.now() >>> 0` is re-minted on Retry by the same expression that
mints it at run start. Two run starts inside the same millisecond therefore draw the same
board sequence. This plan deliberately does NOT introduce a new seed policy: that would be a
Phase-10-adjacent determinism decision, and the property is unchanged from the shipped
behaviour. It cannot inflate `bestWave` (each run still records its own wave), so it is
recorded, not fixed.
