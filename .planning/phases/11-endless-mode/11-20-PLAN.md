evidence that does not support it.

## The claim, link by link, as it will be written

1. `injectCertWorstCase` has exactly one statement: it increments `certRequest.value`
   (`src/runtime/useGameLoop.ts:784-789`). It applies nothing itself.
2. The only consumer of that request is the block at `src/runtime/useGameLoop.ts:440-444`, which
   tests `certRequest.value !== certApplied.value`, syncs `certApplied` and calls
   `applyCertWorstCaseInject`. That block is inside `onFrame`.
3. `onFrame` runs only while the frame callback is active: `useFrameCallback(onFrame, false)`
   (`:685`) starts inactive and `setActive` (`:691-694`) is the only thing that arms it. On this
   branch `setActive(false)` has already run.
4. Nothing resets `certRequest` or `certApplied` on a retry, a level change, a mode change or a
   run boundary — `certApplied.value` is assigned exactly once in the file, at the consume site.
5. Therefore the request survives, and the load applies on the FIRST FRAME OF THE NEXT RUN that
   arms the loop. On that frame the retry-reset block at `:412-438` runs first, so the load lands
   BELOW it — onto the freshly reset world, not onto the dead one.
