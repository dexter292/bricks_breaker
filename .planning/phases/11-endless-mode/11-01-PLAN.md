## Decision made here, not deferred to the executor: `world.tick` across waves (D-06)

**`applyWaveAdvance` sets `world.tick = 0`. Each wave starts at serve speed.**

Why: E2's speed ramp is a pure function of `world.tick` — `360 * (1 + 0.01 * tick/120)`,
clamped at `MAX_BALL_SPEED = 720`, so the cap is reached at t = 100 s
(`src/core/rules/speedRamp.ts:21-35`). The measured d=20 median wave is 172.5 s, so the cap
lands *inside wave 1*. Carrying `tick` would pin every ball at 720 from roughly wave 3
onward forever, which makes D-02's wave→difficulty ramp cosmetic: the real difficulty dial
would silently become "the ball is at the cap", not the generator's difficulty input.
Research measured both policies over 30 waves at one run seed: carried = 3457.4 s /
791 190 points; reset = 4497.2 s / 946 880 points. Resetting also matches the contract every
campaign level already has — a board starts at serve speed.

Two consequences this plan and plan 11-03 own:

1. **Effects must be cleared before the `tick` reset.** `effectUntilTick` is an absolute
   tick value; clearing after the reset would turn a live 10-second expand into a permanent
   one. The ordering is load-bearing and carries a comment saying so (Task 1).
2. **`ticksPlayed` telemetry would truncate to the final wave.** Banked in plan 11-03 on the
   UI runtime, where the reset happens — see that plan's objective for why the bank is not
   an app-tier ref.

Alternative rejected: carrying `tick`. It reads as "the run gets harder", but it makes the
written-down ramp (SC-2) not the thing that controls difficulty, which is a direct conflict
with the requirement.

## Second decision made here: `lowestLiveBall` is exported (D-07)

`tests/helpers/balanceBot.ts:85` keeps `lowestLiveBall` private and the research prototype
inlined a copy. Two files in this phase need the same four-line scan. Export it from the
helper rather than duplicating it — one bot policy, one definition.
