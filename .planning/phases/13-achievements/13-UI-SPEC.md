# Phase 13 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

## What this contract covers, and what it deliberately does not

`13-CONTEXT.md` D-01..D-17 are **LOCKED**. This phase adds **one block to two existing panels**
and nothing else. There is no new screen, no toast layer, no queue, no new state machine.

| Surface | Exists because | Locked input |
|---------|----------------|--------------|
| **S1** Unlock block inside `ResultOverlay` (campaign + endless) | D-06 — the result panel the player is already looking at | D-05, D-06, D-07, D-08 |
| **S2** The same block inside `DailyResultOverlay` | D-06 — daily has its own panel | D-05, D-06, D-07, D-08 |

S1 and S2 are **one block rendered by one shared pure function**, not two designs. The only thing
that differs between them is where in each panel's locked line order it sits.

**Explicit non-goals:**

- **The Achievements screen.** Phase 14 (`N-UI-01` / `N-UI-02`) owns locked/unlocked entries,
  descriptions, recency order and every use of D-14's timestamps. This phase writes that data and
  renders none of it.
- **Any locked-achievement surface.** No "3 bricks from X", no progress bar, no next-up teaser, no
  spoiler-safe locked list. That is Phase 14 SC-3's sentence, and a teaser on a result panel is the
  loss-aversion shape this project has a standing prohibition against (§ Standing Prohibitions).
- **A toast, banner, mid-run HUD field or any in-rally surface.** D-07 satisfies SC-4
  *structurally*: the panel exists only after the run has ended. Nothing in this contract may be
  correct only because of when it fires.
- **Any reward, currency, share affordance or cosmetic.** PROJECT.md rules the category out.

**Continuity:** extends `12-UI-SPEC.md` (approved, in force), which extends `11-UI-SPEC.md` →
`06-UI-SPEC.md` → `03-UI-SPEC.md` + `D1-UI-SPEC.md`. **Phase 13 introduces zero new colors, zero
new type sizes, zero new weights, zero new spacing tokens, zero new `StyleSheet` entries and zero
new packages.** Every number below is read from shipped source or derived from a named font metric
— see [Measurement Provenance](#measurement-provenance).

## The row budget — the measured result that shapes this whole contract

`WINDOWS.md` #17 is an **open, never-observed** backstop: the fully-populated `DailyResultOverlay`
at **320×568pt** has never been seen on a device, jsdom does no layout, and `12-UI-SPEC.md` forbids
scrolling because `Menu` must be reachable. This phase adds rows to that panel and to a second one.
So the budget is computed first, and the design follows from it.

### The row model (every value read from shipped `StyleSheet.create`)

| Row | Scaling part (`lineHeight`) | Fixed part (padding + border + margin) | Height |
|---|---|---|---|
| panel box | — | `padding: 24` × 2 | **48** |
| `heading` | 24 | `marginBottom: 16` | **40** |
| `body` | 24 | `marginBottom: 16` | **40** |
| `metric` | 24 | `marginBottom: 8` | **32** |
| `starsRow` | 24 (`starGlyph`) | `marginBottom: 8` | **32** |
| `badge` | 20 (`badgeLabel`) | `padding: 4` × 2 + `marginBottom: 16` | **44** |
| primary button (`Retry` / `Next`) | 24 (`buttonLabel`) | `paddingVertical: 12` × 2 + `marginTop: 16` | **64** |
| `menuButton` | 20 (`menuLabel`) | `paddingVertical: 12` × 2 + `borderWidth: 1` × 2 + `marginTop: 16` | **62** |

`minHeight: 44` **never binds** on either control: the primary button computes to 48
(12 + 24 + 12) and `menuButton` to 46 (12 + 20 + 12 + 1 + 1). Yoga sizes a content-driven box as
content + padding + border.

> **Correction to `12-UI-SPEC.md` and `WINDOWS.md` #17.** Both record the fully-populated daily
> panel at **456px**. The figure is **458px**: the CTA was counted as 60 (`16 + 44`, the `minHeight`)
> rather than 62, dropping `menuButton`'s two 1px borders. Recorded here rather than silently
> restated, because #17 is still open and a re-measurement must not inherit a 2px optimism.

### The viewport

`IPHONEOS_DEPLOYMENT_TARGET = 16.4` (`ios/PulsePaddle.xcodeproj/project.pbxproj:400`;
`ios/Podfile:25`). iOS 16 will not install on any device smaller than 375×667pt natively, so
320×568 is **not** a native viewport for this build. It is nonetheless reachable: **Display Zoom on
a 375×667 device (iPhone 8 / SE 2nd gen / SE 3rd gen) renders the UI at 320×568 logical points.**
That is why #17's viewport is the right floor and is kept.

`ios/` exists and `android/` does not — iOS is the only configured platform, consistent with
PROJECT.md ("iOS, Android deferred").

Usable height = `568 − top inset 20 − bottom inset 0 = **548**`. Top inset 20 because the status
bar is **visible** (`app/_layout.tsx:25`, `<StatusBar style="light" />`, never `hidden`); bottom
inset 0 because a home-button device has no home indicator. **Both insets are device-supplied and
are an assumption here, not a measurement** — see [Measurement Provenance](#measurement-provenance).

### Panel heights today, before this phase

| Panel state | Height | Headroom in 548 |
|---|---|---|
| `ResultOverlay` **campaign win** — 3 stars + `New Record` + `Next` | **458** | **90** |
| `ResultOverlay` campaign lose + `New Record` | 362 | 186 |
| `ResultOverlay` **endless** + `New Record` | 426 | 122 |
| `DailyResultOverlay` closed, **badge** branch (10 rows) | 426 | 122 |
| `DailyResultOverlay` closed, **streak-ended** branch (10 rows) | 414 | 134 |
| `DailyResultOverlay` board-failure (open date) | 350 | 198 |

**The daily panel's real maximum is 10 rows, not 11.** The badge and the streak-ended line are
**mutually exclusive by derivation**: the streak-ended line renders only on the first date of a new
streak, where `streak === 1`, and `showBadge` requires `streak >= 2`
(`DailyResultOverlay.tsx`). So `12-UI-SPEC.md`'s and #17's "fully-populated 11-row" panel is
**unreachable through the contracted host derivation**.

It is, however, **not enforced by the component** — `DailyResultOverlay` folds
`endedStreakLength` and `streak` independently and would render both if a host handed it both. So
the 11-row figure is kept as a **defensive bound (458px, 90px headroom)** and this contract budgets
against it. Naming a gate that does not exist is the failure mode this project has produced three
times; the exclusion is a property of the host's derivation, and only there.

### Adding the achievement block

Each unlock line is a `metric` row: **32px** (24 lineHeight + 8 marginBottom).

| Panel state | +1 row | +2 rows | +3 rows | +4 rows |
|---|---|---|---|---|
| **campaign win (binding case)** | 490 ✅ 58 spare | **522 ✅ 26 spare** | 554 ❌ **over by 6** | 586 ❌ over by 38 |
| endless | 458 ✅ 90 | 490 ✅ 58 | 522 ✅ 26 | 554 ❌ over by 6 |
| daily, badge branch | 458 ✅ 90 | 490 ✅ 58 | 522 ✅ 26 | 554 ❌ over by 6 |
| daily, defensive 11-row bound | 490 ✅ 58 | **522 ✅ 26** | 554 ❌ over by 6 | 586 ❌ over by 38 |
| campaign lose | 394 ✅ | 426 ✅ | 458 ✅ | 490 ✅ |
| daily board-failure | 382 ✅ | 414 ✅ | 446 ✅ | 478 ✅ |

### Verdict: **D-05's shape (3 named lines + a count line = 4 rows) does not fit at 320×568.**

It overruns the campaign-win panel by **38px** and the defensive daily bound by **38px**. Three
rows still overrun both by **6px**. **Two rows fit every state of both panels with 26px to spare**,
and 26px is the tightest margin anywhere in the table.

The binding case is **`ResultOverlay` campaign win with 3 stars, `New Record` and `Next`** — and it
is not exotic. It is a cleared level, all lives kept, a beaten personal best, with a next level to
play: precisely the run most likely to unlock something, and precisely the run D-04's retroactive
flood lands on if the player's first run after installing this build is a good campaign run.

**The campaign/endless panel is therefore the tighter of the two, not the daily one.** The risk that
earned this UI pass pointed at `DailyResultOverlay`; the measurement moves it to `ResultOverlay`.

### The reduction

**`ACHIEVEMENT_LINES_MAX = 2`.** At most two rows, on both panels, in every state.

| Newly unlocked, `n` | Rows rendered |
|---|---|
| 0 | **none** — the block is absent |
| 1 | `Unlocked · {name₁}` |
| 2 | `Unlocked · {name₁}` · `Unlocked · {name₂}` |
| ≥ 3 | `Unlocked · {name₁}` · `and {n − 1} more` |

This keeps D-05's **shape** — name what can be named, count the rest, never a bare count and never
a scroll — at the largest size the arithmetic permits. D-05's own reversibility note applies
verbatim: *"the cap is a single constant"*. Raising it back to 3 or 4 is a one-line change the
moment the device backstop below returns real headroom.

**Rejected reductions, and why:**

| Option | Rejected because |
|---|---|
| Keep 4 rows, shrink the panel padding / touch targets / type scale | `12-UI-SPEC.md` § Layout rules forbids all three by name |
| Keep 4 rows, make the panel scrollable | D-05 rejected it and `12-UI-SPEC.md` forbids it — `Menu` must be reachable without scrolling |
| Render the block at the **Label** token (14/20) to buy rows | 4 rows at 14/20 + `mb: 8` is 112px — still over the campaign-win 90px budget. It buys nothing and mixes a second size into the panel body |
| Render at Label 14/20 + `mb: 4` (24px/row) | 4 rows is 96px — over by 6px. Still fails, and now costs a denser row *and* a smaller size for no fit |
| A different cap per panel (3 on daily, 2 on campaign) | The same unlock event would read differently depending on which mode you finished in, and it doubles the copy shapes under test. It also does not help: the daily defensive bound is 90px, identical to campaign win |
| Cap adaptive to `useWindowDimensions()` | Correct engineering, wrong phase: it makes the copy a function of the viewport, adds a branch jsdom cannot verify, and puts a second answer to "how many lines" in the tree |
| Drop a shipped line to make room (`Days played ·`, `Best ·`) | `12-UI-SPEC.md` sanctions dropping `Days played ·` only as a *last* remedy for the daily panel, and it does nothing for the binding campaign-win case |

### Named cost, accepted

A retroactive flood (D-04) of 8–12 unlocks names **one** of them and counts the other 7–11. The
player is told the total and one title, and — until Phase 14 ships the Achievements screen —
**has no surface anywhere that lists the rest.** That is a real gap in the phase goal's "tells
them", it is a direct consequence of the measured budget rather than a preference, and it is stated
here so a later round finds a decision rather than a defect.

### Dynamic Type — an amplifier neither prior contract named

**Measured in the installed tree, not recalled:**

- `allowFontScaling` defaults to **true**: `processedProps.allowFontScaling = allowFontScaling !== false;`
  — `node_modules/react-native/Libraries/Text/Text.js:289`.
- An explicit `lineHeight` **also** scales:
  `CGFloat lineHeight = textAttributes.lineHeight * RCTEffectiveFontSizeMultiplierFromTextAttributes(textAttributes);`
  — `RCTAttributedTextUtils.mm:230`.
- Nothing in `src/` or `app/` sets `allowFontScaling` or `maxFontSizeMultiplier` (grep, 0 hits).

So every overlay row's *text* part scales with the system text size while its *fixed* part does
not. Solving `fixed + text × m ≤ 548` for the campaign-win panel:

| Block size | Panel at m = 1 | Largest text multiplier that still fits |
|---|---|---|
| today (no block) | 458 | **m ≤ 1.433** |
| +1 row | 490 | m ≤ 1.250 |
| **+2 rows (this contract)** | **522** | **m ≤ 1.102** |
| +3 rows | 554 | already over at m = 1 |

iOS content-size multipliers relative to the Large default are ≈1.118 (xLarge), ≈1.235 (xxLarge),
≈1.353 (xxxLarge), ≈1.65 and up for the accessibility sizes. So at 320×568 the campaign-win panel
**today** survives every non-accessibility size and clips at AX1; **with this phase's two rows** it
clips one step above the default.

**This contract does not change that, and must not be read as having fixed it.**

- It is **not** created by this phase — the panel is already over budget at AX1 today, and the
  same arithmetic applies to `12-UI-SPEC.md`'s shipped rows.
- The combination is **correlated, not independent**: 320×568 is only reachable via Display Zoom,
  which is itself a legibility setting, so a player at that viewport is more likely than average to
  have raised their text size too.
- The one available lever is `maxFontSizeMultiplier`, which React Native honours
  (`RCTAttributedTextUtils.mm:117`, `fminf(maxFontSizeMultiplier, fontSizeMultiplier)`). Applying
  it to the overlay panels is an accessibility trade-off across three shipped components and is an
  **owner decision, explicitly out of scope for this phase.** It is named here so the decision
  exists to be taken.

This is registered as a `backstop` in [§ UI Considerations](#ui-considerations) and must be carried
into `WINDOWS.md` alongside the successor to #17.

### At 375×667 (the native floor) the constraint disappears

Usable 647. Campaign win is 458 with **189px** of headroom, and **4 rows fit with 61px to spare**
(m ≤ 1.201). The entire reduction is a 320×568 artifact. If the device backstop is discharged and
the product decides Display Zoom is out of support, `ACHIEVEMENT_LINES_MAX` goes to 4 with no other
change to this contract.

## Copywriting Contract

Exact strings. `·` is U+00B7 MIDDLE DOT, matching every shipped metric line. Every string is a
fixed English literal plus an integer and an authored achievement name. There is no user input and
no i18n path in this phase.

### The block

| # | Element | Copy | Renders when |
|---|---------|------|--------------|
| 1 | First unlock | `Unlocked · {name₁}` | `n ≥ 1` |
| 2a | Second unlock | `Unlocked · {name₂}` | `n === 2` |
| 2b | Overflow | `and {n − 1} more` | `n ≥ 3` |

`n` is the count of achievements newly unlocked by **this** run (D-02's set difference). The two
forms of row 2 are mutually exclusive.

**Line count is always 0, 1 or 2. Never 3, in any state, on either panel.**

**Copy rationale, stated because each choice was available to get wrong:**

- **`Unlocked ·` and not `Achievement unlocked`** — 21 characters of prefix would leave 6 for the
  name against the measured 27-character budget. `Unlocked ·` is 11 and matches the `·` form of
  every other line on both panels, so the block reads as part of the panel rather than as a
  notification pasted onto it.
- **`and {n − 1} more` and not `… and {n − 1} more`** — no leading ellipsis. The lowercase `and`
  already reads as a continuation of the line above, and dropping U+2026 keeps the visible copy
  inside the ASCII + U+00B7 set every shipped line uses. (U+2026 **is** present in the shipped font
  — glyph 592, verified in the `cmap` — so this is a style choice, not a tofu avoidance.)
- **No "Achievements" heading row.** It would cost a third row, which does not fit, and
  `Unlocked ·` already says what the block is.
- **No `!`, no "Congratulations", no "Nice!"** — every other line on these panels states a fact.
- **No count-only form.** D-05 rejected a bare count: it tells the player something happened
  without telling them what. `n ≥ 3` still names one.
- **No total-progress line** (`7 of 12 unlocked`). It is a completion meter, it costs a row that
  does not exist, and it belongs to Phase 14's screen.

### The zero state is an absence, not an empty state

`n === 0` renders **nothing** — no block, no divider, no reserved space, no placeholder.

There is no `No achievements this run` line, and that is contract. It would cost 32px on **every**
result panel forever to say nothing, and phrased at all it becomes a small reproach at the end of a
run the player just lost. Absence is the honest and the cheap answer.

### Error state

**There is none, and no error copy exists in this phase.** Every failure degrades to the zero state:

| Failure | Behaviour | Copy |
|---|---|---|
| The achievements field is missing, unknown-id, or degraded by `sanitizeTelemetry` (D-15) | The host passes fewer names, or none; the block shrinks or disappears | none |
| The unlock write fails | The panel still renders whatever the in-memory evaluation produced; the unlock re-fires on the next run end, because D-02 is a set difference and an unpersisted id is still "not in the stored set" | none |
| The evaluator throws | The host passes no names; the block is absent and the run's own result is unaffected | none |

**No error modal, no banner, no toast anywhere in this phase** (inherited, `06-UI-SPEC.md`).
Achievements are the least load-bearing thing on either panel: a failure here must never obscure
the score, the record or the way out.

### Destructive confirmation

**None, anywhere in this phase.** Nothing in this phase deletes, resets or spends anything. D-17
makes an unlock one-way, so there is no "clear achievements" affordance to confirm and none may be
added.

### The 16-character name budget

Panel text width = `320 maxWidth − 24 padding × 2 = **272px**`. SpaceMono is monospaced at
**0.612 em** (`unitsPerEm` 1000, every `hmtx` advance 612 — parsed from the shipped
`assets/fonts/SpaceMono-Regular.ttf`). At Body 16px that is `16 × 0.612 = 9.792px` per character
and `⌊272 / 9.792⌋ = **27 characters**` per line.

`Unlocked · ` is 11 characters. **Every achievement display name must therefore be ≤ 16
characters.** That is a contract on the catalog the planner authors, not a suggestion.

It is **load-bearing for the vertical budget**, not just for tidiness: a 17-character name wraps to
a second visual line, silently adding 24px, and 24px is most of the 26px of spare height the whole
reduction bought.

Two independent controls, because one of them is a layout property jsdom cannot see:

1. **A catalog assertion** — every display name in the catalog is ≤ 16 characters. This is a plain
   string-length test over exported data, needs no layout, and is therefore `explicit` evidence
   that owes a test case. It is the primary control.
2. **`numberOfLines={1}` on the unlock lines** — the backstop. It converts a catalog authoring
   mistake from *"`Menu` is clipped off the bottom of the panel"* into *"a name is visibly
   truncated"*, which is the strictly better failure. It is a deliberate deviation from every other
   line in both panels and is recorded as one.

The overflow line is never at risk: with a catalog of 8–12 (D-09) and one name shown, the largest
form is `and 11 more` at 11 characters.

### Accessibility labels

`·` is announced inconsistently across screen readers, and the visible strings are terse, so both
line kinds carry a spoken label — the same convention `12-UI-SPEC.md` set for `Streak · {n}`.

| Readout | `accessibilityLabel` | Note |
|---|---|---|
| `Unlocked · {name}` | `Achievement unlocked: {name}` | new |
| `and {n} more` | `And {n} more achievements unlocked` | new — the bare visible string is not a sentence on its own |

Every inherited label in `11-UI-SPEC.md` and `12-UI-SPEC.md` is unchanged. **This phase changes no
existing `accessibilityLabel` and adds no control**, so no `accessibilityRole="button"` is
introduced: the block is non-interactive text.

## Interaction Contract

### The block is non-interactive

**Required.** The unlock lines are `Text`, never `Pressable`. There is nothing to tap, nothing
expands, nothing navigates. Phase 14 owns the screen an unlock line would want to link to, and a
control that has nowhere to go must not render — the same rule that keeps `Retry` off a closed
daily date.

This also keeps SC-4 structural (D-07): the block adds no control, no timer and no state machine,
so there is no timing for it to get wrong.

### One shared pure classifier, two panels

**Required.** The visible text and the spoken label are produced by **one exported pure function**,
imported by both panels:

```
src/runtime/overlays/achievementLines.ts

export const ACHIEVEMENT_LINES_MAX = 2;

export type AchievementLine =
  | { kind: 'name';     text: string; label: string }
  | { kind: 'overflow'; text: string; label: string };

export function achievementLines(
  names: readonly string[],
): readonly AchievementLine[];   // length is always 0, 1 or 2
```

This mirrors the two shipped precedents exactly — `waveBuildFailureKind` in `ResultOverlay.tsx` and
`countdownForm` in `DailyResultOverlay.tsx` — and for the reason `countdownForm`'s own JSDoc gives:
*"so the visible line and the spoken label can never disagree about which case they are in. Two
readers deriving the same boundary independently is how they come to disagree."* Here there are
literally two readers — two panel files maintained in parallel — so the risk is not hypothetical.

`src/runtime/overlays/` is inside the `runtime` boundary, which `eslint.config.js`
`boundaries/dependencies` permits `runtime` to import.

Required properties of the function, all observable in jsdom without layout:

| Property | Why it is contract |
|---|---|
| Returns at most `ACHIEVEMENT_LINES_MAX` entries for **any** input, including a 50-element array | The cap is a property of the component, not a promise by the host. A host bug must not be able to push `Menu` off-screen |
| Pure — no clock, no storage, no randomness | SC-2's determinism reaches the panel, not just the evaluator (D-03) |
| Preserves input order; never sorts, never dedupes | See § Ordering below |
| Total over hostile input — a non-string, empty or whitespace-only entry is **dropped**, and `n` is the count after dropping | Degrades downward, like every other v4 read path (D-15). It never invents a name and never inflates the count |

### Ordering is contract

**The host passes `unlockedAchievements` in catalog declaration order, and the panel never
re-sorts.**

Not recency: under D-04's retroactive flood every unlock carries the *same* timestamp — the one
`recordRunEnd` that evaluated them — so recency order is arbitrary there and would make the named
achievement vary between two runs of the same snapshot, breaking SC-2 at the surface the player
actually sees. Not alphabetical: it is meaningless to the player and it re-orders whenever a name
is edited. Catalog order is stable, authored, and lets the catalog author put the achievement most
worth naming first — which is exactly the decision the `n ≥ 3` case needs someone to have made.

### Props — scalars and strings only (D-08)

**Required.** Both panels gain one prop:

```
unlockedAchievements?: readonly string[];   // default []
```

An array of display-name strings. **Never** an `AchievementId`, never a catalog record, never an
unlock record, never a `TelemetryBlob` field, never a timestamp. `eslint.config.js`
`boundaries/dependencies` forbids `src/runtime` importing `src/services`, **and no unit test
observes that boundary — `npm run lint` is the only thing holding it.** Phase 12 learned this on
`DailyResultOverlay`; the same discipline and the same gate apply.

`ResultOverlay`'s `mode` prop stays `'campaign' | 'endless'` and is **not** widened.
`DailyResultOverlay` stays a separate component. Nothing about the phase-12 separation changes.

### Where the block sits — each panel's line order, extended

**`ResultOverlay`** (heading → body → `Wave ·`? → `Score ·` → `Best ·` → `Best wave ·`? → stars? →
badge? → **unlock block** → `Retry` → `Next`? → `Menu`)

**`DailyResultOverlay`** (heading → body → `Daily ·` → `Score ·` → `Streak ·` → `Best streak ·` →
`Days played ·` → streak-ended? → badge? → **unlock block** → countdown → `Menu`)

The block sits **after the badge and before the controls** on both. The reading is *what happened →
your numbers → your records → what you earned → the way out*. On the daily panel it goes **above**
the countdown, because `12-UI-SPEC.md` placed the countdown last on purpose — *"so it reads as a
footnote"* — and an unlock is not a footnote.

No divider, no rule, no extra gap is introduced at either seam. The block's last line carries
`marginBottom: 8` and the following element carries its own `marginTop: 16` (`retrySpaced` /
`buttonSpaced`) or `marginBottom: 8` (the countdown `metric`) — the existing rhythm, unchanged.

### When the block is suppressed — reusing shipped flags, adding none

| Panel | Suppressed when | Flag |
|---|---|---|
| `ResultOverlay` | `waveBuildFailureKind(waveBuildFailedWave) === 'start'` | the **existing** `showRunLines` |
| `DailyResultOverlay` | `kind === 'board-failure'` | the **existing** `isClosed` |

Both reuse a boundary the phase-11 / phase-12 work already named and tested. **No new suppression
flag is introduced,** because a second flag meaning "is there a run" is a second place for the
answer to drift — the defect family `11-UI-SPEC.md` exists to close.

The reasoning is identical in both cases and is the same sentence: *the block describes a run, and
in these two states there is no run.* At endless Retry time (`'start'`) no run has happened yet, so
any names still in props belong to the **previous** run and would be re-announced under failure
copy. On a daily board failure nothing was played, nothing was written, `recordRunEnd` never ran,
and the date is still open.

`'mid'` is **not** suppressed: a mid-run wave-build failure ends and *saves* the run,
`recordRunEnd` did run, and the unlocks are real.

### Determinism at the surface (SC-2)

Rendering the same `unlockedAchievements` array twice produces byte-identical lines. The classifier
is pure, the panel injects no clock for this block, and nothing about the block depends on mount
order or on how many times the panel has rendered. This is observable in jsdom and owes a test.

### Shell rules (unchanged, restated)

- `PlayingHost` still unmounts when not playing; `Menu` returns to Title.
- Safe-area insets, AppState auto-pause, `Resume` → 3·2·1 countdown — all unchanged. An unlock
  never triggers a countdown, a pause, a haptic, a sound or a screen shake. **No juice is attached
  to an unlock this phase**: `D1-UI-SPEC.md`'s effects are gameplay feedback on a live board, and
  the panel exists only after the board is gone.
- `HudStrip` gains **no** achievement field, no counter, no icon. Unchanged file. Mid-run is when
  the unlock set cannot change, and a production HUD surface is `N-UI-01`'s to add.
- Forbidden UI, unchanged: no ad banner or interstitial, no shop, no rewarded continue, no sign-in,
  no IAP price label.

### Standing Prohibitions (carried forward and extended)

`12-UI-SPEC.md` carries a standing prohibition against shaming, guilt framing and any offer to
restore / protect / buy. PROJECT.md rules out ads, shop, IAP, accounts and social entirely. An
achievement surface is exactly where that pressure reappears, so it is restated with the specific
shapes this phase would invite:

- **No progress teaser.** No "2 more bricks for X", no percentage, no bar, no "so close".
- **No locked-achievement preview** on a result panel, spoilered or not.
- **No scarcity, urgency or streak-protection framing.** Nothing is limited-time, nothing expires,
  nothing can be lost — D-17 makes an unlock one-way and the copy must not imply otherwise.
- **No reward, currency, cosmetic, unlockable or "claim" action.** None exist and none may be
  implied by the copy.
- **No share, invite, leaderboard or compare affordance.** PROJECT.md: offline-first, no server,
  no account, no social.
- **No reproach for a run that unlocked nothing.** The zero state is silence.

render is not evidence that the panel fits, and must not be recorded as having verified one.

**What jsdom can observe, and must.** The limit is layout, and only layout. These are `explicit`

- The block is absent at `n = 0`.
