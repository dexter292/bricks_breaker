**The sanitizer.** Two functions, mirroring `sanitizeDailyHistoryEntry` + `sanitizeDailyRecord`,
placed beside them in the same file.

`sanitizeAchievementUnlock(raw: unknown): AchievementUnlock | null` — total over `unknown`. Return
`null` when `raw` is not an object, or when `isKnownAchievementId(entry.id)` is false. Import
`isKnownAchievementId` from `'../achievements'`, across the module boundary, exactly as
`isValidDateKey` is imported from `'../daily'` today — and say in the JSDoc that the parser must
NOT restate the catalog's ids, for the reason `isValidDateKey` gives: the predicate lives beside
the derivation it guards, so a catalog change cannot leave a stale copy in the parser.

**The timestamp is the divergence and it needs its own paragraph.** `sanitizeRunLogEntry` in this
same file drops the whole entry when `timestamp` is not a finite number, and
`sanitizeDailyHistoryEntry` has no timestamp at all — so the shipped drop-on-invalid rule is the
WRONG analog and a later reader will reach for it. D-15 says a malformed timestamp DEFAULTS and
D-17 says an unlock is one-way; dropping the entry would un-earn an achievement, which is the one
thing this phase forbids. So the id and the timestamp take DIFFERENT failure rules inside one
entry sanitizer — bad id drops the entry, bad `at` takes the local `safeCounter`'s zero and keeps
it. There is no in-repo precedent for two rules in one entry sanitizer; write the reason into the
JSDoc, because a later reader will otherwise unify them and the unification is silent.

`sanitizeAchievementRecord(raw: unknown): AchievementRecord` — start from
`defaultAchievementRecord()`; return it unchanged when `raw` is not an object or when the
`unlocked` position is not an array. Otherwise: drop-invalid per entry into a local array, then
DE-DUPLICATE by id keeping the EARLIEST `at`, then `slice(-ACHIEVEMENT_UNLOCK_BOUND)`. The
drop-then-trim order is contract and carries the daily record's own comment adapted — bound on
read as well as on write, applied AFTER the drop loop, because trimming first would let padding
garbage push real unlocks out of the window.

De-duplication is legitimate here where it is not for dates, and the JSDoc must say why the
neighbouring rule is weaker rather than copying its sentence: `sanitizeDailyRecord` refuses to
re-sort because sorting would REPAIR a tampered blob into a longer streak than its own stored
order can justify. An unlock set is unordered, D-14's timestamps are the recency key, and
`13-UI-SPEC.md` makes CATALOG DECLARATION ORDER the display order, derived in the host and not in
storage — so there is no order here to inflate. De-dup by id is therefore safe, and earliest-wins
is required for the same reason D-22 requires it in the merge.
