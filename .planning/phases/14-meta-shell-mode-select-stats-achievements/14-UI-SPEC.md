# Phase 14 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

## What this contract covers, and what it deliberately does not

`14-CONTEXT.md` D-01..D-15 are **LOCKED** and are not re-argued here. This contract does three
things and nothing else: it **budgets three screens** against the measured 548 pt usable height,
it **picks `maxFontSizeMultiplier`** (the lever D-18 / `WINDOWS.md` #29 deferred to this phase),
and it fixes the copy, colour and interaction rules for the two new screens.

| Surface | Exists because | Locked input |
|---|---|---|
| **S1** `TitleScreen` extended to seven rows | D-01, D-02 | D-01, D-02, D-03, D-05, D-07 |
| **S2** `StatisticsScreen` (new) | D-15 / N-STAT-03 / SC-2 | D-15 |
| **S3** `AchievementsScreen` (new) | D-08..D-13 / SC-3 | D-08, D-09, D-10, D-11, D-12, D-13 |
| **S4** `maxFontSizeMultiplier` across every shell and overlay `Text` | D-18 / #29, due at this phase | D-03 |

**Explicit non-goals.** No new game mode, no new achievement, no change to what telemetry
records, no tiering or rewards (D-09 rejected it), no cloud sync or social comparison
(`PROJECT.md` rules the category out), **no `recentRuns` surface** (D-15), no countdown on Title
(deferred), no best-streak row (deferred — and already rendered by the daily result panel), no
progress meter on a locked achievement (D-09), **no tab pattern** (D-01 and D-02 both rejected
one and this shell has never had one), and **no ads, shop, login or account chrome** (`PROJECT.md`
§ Out of Scope, D-18, restated in `TitleScreen`'s own header).

**Continuity.** Extends `13-UI-SPEC.md` (approved, in force) → `12-UI-SPEC.md` → `11-UI-SPEC.md`
→ `06-UI-SPEC.md` → `03-UI-SPEC.md` + `D1-UI-SPEC.md`. **Phase 14 introduces zero new colours,
zero new type sizes, zero new weights, zero new spacing tokens, zero new fonts and zero new
packages.** Every number below is measured on a device, read from shipped source, or computed from
a named font metric — see [Measurement Provenance](#measurement-provenance).

**One new constant is introduced** (`MAX_FONT_SCALE`) and
[§ The multiplier](#the-multiplier--discharging-d-18--29) names the twelve production files that
read it, because this project has shipped a constant that nothing read
(`ACHIEVEMENT_LINES_MAX` before `99afd8b`) and described it in three artifacts as the single place
the number lived.

## The budget — the arithmetic this contract exists to settle

D-03 is what makes this document load-bearing: **Title is budgeted to fit at 320×568 and never
scrolls**, on `12-UI-SPEC.md`'s rule that *a control the player cannot reach is a defect, not
cosmetic overflow*.

### What is already measured, and is not re-derived here

Four readings taken **2026-09-29** are the inputs. They are not recomputed.

| Input | Value | Source |
|---|---|---|
| Bottom safe-area inset, iPhone SE class | **0** (`t=20 b=0 l=0 r=0`) | `useSafeAreaInsets()` read on an iPhone SE (3rd generation) simulator — #28 partial discharge |
| **Usable height at 320×568** | **548 pt** = 568 − 20 − 0 | arithmetic over a measured inset, no longer an assumption |
| Per-row arithmetic model | validated to **half a point** (7-text-row panel measured 361.5 vs modelled 362) | #28 partial discharge |
| The 11-row binding panel | measured **484 pt** against a modelled 522 — **the model is conservative by 38 pt**; spare is **64 pt**, not 26 | #28 third measurement |
| 16-character display-name budget | holds with margin — 27 chars rendered on one line, ink 261.5 pt inside a 312 pt panel; the real SpaceMono advance is slightly **narrower** than the assumed 0.612 em | #16 discharge |
| Dynamic Type growth | **+20.0 pt across 7 text rows** at `extra-large`, ≈**2.86 pt per row** (panel 361.5 → 381.5) | #29 observation, `xcrun simctl ui <device> content_size extra-large` |

> **The trap #29 records, restated because this whole section depends on not falling into it.**
> The panel **height** ratio at `extra-large` is 1.0553, and that is **not** the **text**
> multiplier a spec quotes. Fixed padding, borders and button chrome do not scale, so the panel
> always grows by **less** than the font does. Reading `1.0553 < 1.102` as "it does not clip"
> compares two different quantities. **Every projection below uses absolute per-row growth.**

### The model

Each row is split into a **scaling part** (its `lineHeight`, which iOS multiplies — measured at
`RCTAttributedTextUtils.mm:230`) and a **fixed part** (padding, border, margin, which it does not).

```
H(m) = F + S · g(m)          where  g(m) = 1 + k·(m − 1)
```

`k` is calibrated from the #29 reading, **not assumed to be 1**: the measured panel's nominal
scaling total is `24×5 + 20×2 = 160`, it grew 20.0 pt at `m = 1.118`, so
`k = (20.0 / 160) / 0.118 = **1.0593**`. Growth runs **5.93 % above** the nominal `lineHeight`
sum. Using `k = 1` would understate every projection here.

and two rows for endless and daily. `recentRuns` is not rendered (D-15) and is not budgeted.

|---|---|---|---|---|

**The lifetime block is exactly three rows, and that is a contract, not a starting point.** A

2. `Best combo` ← `lifetime.bestComboEver` (`25x Combo`)

needed is `Longest rally`.** Recorded here so a later author finds a decision rather than inventing
one.

**A total-pickups row is excluded by D-15, not by the budget.** `100 Pickups` is the sum of five
fields (`pickupMultiball` + `Expand` + `ExtraLife` + `Slow` + `Fireball`); D-15 says the screen
reads `telemetry.lifetime` and `telemetry.byMode` **directly** and derives nothing. A summed row
would be the one derived value on the screen. **`Best streak` is excluded because it is already
rendered**: `Best streak · {longestStreak}` is a shipped line in `DailyResultOverlay.tsx:348`, and
D-06 makes that panel reachable from Title. One renderer for one truth (`12-UI-SPEC.md`).

### S3 — Achievements, twelve entries. This screen scrolls.

Twelve entries with names and descriptions do not fit 548 pt, and no reduction inside D-08's rule
(*every entry shows its condition; nothing is hidden*) makes them fit.

Description wrapping, computed: the entry text box is **272 pt** (`paddingHorizontal: 24`, no row
padding). At Label 14 px the advance is `14 × 0.612 = 8.568 pt`, so `⌊272 / 8.568⌋` = **31
characters per line**. Greedy word-wrap over the twelve shipped descriptions gives **2 lines for
the worst case** — the longest are `Set off a single chain reaction that breaks 12 bricks` (53) and
`Win a daily challenge having never lost a life on one` (53).

| Part | Fixed | Scaling | Height |
|---|---|---|---|
| Fixed header: `paddingTop: 8` + `Back` 46 + heading `marginTop: 24` + `lineHeight: 24` | 58 | 44 | **102** |
| One entry: name `lineHeight: 24` + `marginTop: 4` + description 2 × `lineHeight: 20` | 4 | 64 | **68** |
| Inter-entry `gap: 16` | 16 | 0 | **16** |

Twelve entries: `12 × 68 + 11 × 16 = 992`, plus a `paddingBottom: 24` = **1016 pt** of content
against **446 pt** of viewport below the fixed header. **Over by 570 pt — more than one whole
extra viewport.** There is no arrangement of twelve name-plus-description entries that fits.

#### Does D-03 bind this screen? No — and here is the reason, stated rather than assumed

D-03's own words scope it: *"**Title** is budgeted to fit at 320×568 and never scrolls."* The
**reason** it inherits from `12-UI-SPEC.md` is narrower than "screens must not scroll" — it is
that **a control the player cannot reach is a defect**. Title is seven controls, so the rule binds
it absolutely. The Achievements screen is **one control (`Back`) plus data**, so the rule is
honoured by keeping that one control reachable, not by refusing to scroll.

**The scroll is therefore sanctioned here, under three conditions that are contract:**

1. **`Back` sits in a fixed header, outside the scroll view.** It is reachable at every scroll
   offset. This is the entire content of the rule D-03 inherits, and it is what makes a scroll
   here different from the scroll `12-UI-SPEC.md` forbade on the result panels — there, `Menu`
   was *inside* the scrolling region.
2. **The screen heading is in the same fixed header**, so the player always knows what they are
   looking at.
3. **At least the first two entries — name, state marker and the complete description — are fully
   visible without scrolling.** Computed: **5 entries at `m = 1`** (`5 × 68 + 4 × 16 = 404` inside
   446) and **3 at the 1.2 cap** (descriptions reach 3 lines there, see below), so the contract's
   two is met with margin at both ends.

The list **never re-sorts** (D-10, catalog declaration order), so a scroll position means the same
thing on every visit. That is what makes scrolling acceptable rather than merely tolerable.

**The Statistics screen does not scroll**, because it fits (458 / 548). D-15's own rationale for
excluding `recentRuns` was to keep it that way, and this contract keeps that promise.

### The multiplier — discharging D-18 / #29

**`allowFontScaling` defaults to `true`** (`node_modules/react-native/Libraries/Text/Text.js:289`)
and an explicit `lineHeight` **also** scales (`RCTAttributedTextUtils.mm:230`), so every row's text
part grows with the system text size while its fixed part does not. Nothing in `src/` or `app/`
sets `allowFontScaling` or `maxFontSizeMultiplier` today. The lever React Native honours is
`maxFontSizeMultiplier` (`RCTAttributedTextUtils.mm:117`, `fminf(maxFontSizeMultiplier,
fontSizeMultiplier)`) — a **continuous** `fminf`, not a snap to an iOS step.

**This contract must budget against the MEASURED 484 pt base, not the modelled 522.** Against the
model there is no useful cap at all: the binding panel's modelled ceiling is already `m ≤ 1.096`,
below iOS `xLarge` at ≈1.118, so a model-based cap would clip at the first step above default no
matter what value it took. #28's third measurement is what makes a real answer possible.

| Surface | `F` | `S` | `H(1)` | spare | own ceiling `m` |
|---|---|---|---|---|---|
| **`ResultOverlay` campaign-win + 2 unlock rows — MEASURED 484** | 228 | 256 | **484** | 64 | **1.236** |
| `TitleScreen`, seven rows | 236 | 232 | 468 | 80 | 1.325 |
| `StatisticsScreen`, 3 + 7 rows | 154 | 304 | 458 | 90 | 1.280 |
| `AchievementsScreen` | — | — | scrolls | n/a | n/a |
| *(the same overlay case, MODELLED 522 — shown to be dismissed)* | *266* | *256* | *522* | *26* | *1.096* |

**The binding surface is the shipped `ResultOverlay`, not any screen this phase adds.** That is
the headline result: D-03 asked for a multiplier that makes seven Title rows fit, and Title turns
out to have 80 pt of spare and a 1.325 ceiling. The number is set by the panel #29 has been
pointing at all along.

## **`MAX_FONT_SCALE = 1.2`**

| Surface | `H(1.2)` | spare at the cap |
|---|---|---|
| `ResultOverlay` campaign-win (binding) | `228 + 256 × 1.2119 = ` **538.2** | **9.8** |
| `TitleScreen` | `236 + 232 × 1.2119 = ` **517.2** | **30.8** |
| `StatisticsScreen` | `154 + 304 × 1.2119 = ` **522.4** | **25.6** |

Why 1.2 and not another value:

- **Above `xLarge` (≈1.118)**, so the single most common Dynamic Type step renders at full size and
  no common user is scaled down at all.
- **Below the binding surface's measured ceiling of 1.236**, by 0.036.
- **Continuous, so nobody is snapped to a step.** A player at `xxLarge` (1.235) gets 1.2 — 97 % of
  what they asked for; at AX5 they still get a 20 % enlargement, where today they get a clipped
  `Menu`.
- **It survives a pessimistic growth assumption.** `k` is calibrated at 1.0593 from a 7-row panel;
  #29 warns that per-row growth is not uniform across different base font sizes. Re-running the
  binding case at `k = 1.5` (growth 50 % above nominal, more than twice the measured excess) gives
  `484 + 256 × 1.5 × 0.2 = 560.8` — over. At `k = 1.25`: `548.0` — exactly at the limit. At the
  measured `k = 1.0593`: `538.2`. **The cap tolerates growth running up to ≈25 % above nominal
  before the binding case clips**, against a measured 5.93 %.

Rejected values: **1.118** (snapping to `xLarge` costs every larger user real legibility and buys
only 22 pt on one surface — and it does not rescue the *modelled* 522 either, so it is not the
"safe" choice it looks like); **1.236** (the measured ceiling itself, zero margin);
**unbounded — today's behaviour** (the binding panel clips one step above default, which is the
defect #29 exists to record).

```

```

`src/runtime/**` is importable by both `src/runtime/**` and `app/**` under
`eslint.config.js` `boundaries/dependencies` (`runtime → runtime`, `app → runtime`), which is why
the constant lives there and not in `app/`.

**Every `Text` in these files carries `maxFontSizeMultiplier={MAX_FONT_SCALE}`.** The `<Text`
counts are `grep -c`, 2026-09-29, pre-change:

| `src/runtime/overlays/PauseOverlay.tsx` | 4 | same overlay stack, must not diverge typographically |

**`SelectScreen` is in scope even though it needs no cap to fit** (its own ceiling is ≈1.94). If
Title caps and `SelectScreen` does not, one tap changes the player's text size — **the cap is a
property of the app's typography, not a per-screen repair.** One constant, one behaviour, every
surface outside the Skia playfield. The Skia playfield renders no `Text` and is untouched.

**The gate is a count equality, not a reading of the diff:** across the twelve files, occurrences
of `maxFontSizeMultiplier` must equal occurrences of `<Text`. Today both sides of the enumerated
set are 56 (`grep -c '<Text'`, and `grep -c '</Text>'` also 56, so there is no self-closing or
nesting confound). The executor re-counts after this phase's two deletions and its additions and
pins the new number. **This is what makes `MAX_FONT_SCALE` a constant that is read rather than
described** — the failure `ACHIEVEMENT_LINES_MAX` shipped with before `99afd8b`.

**#29 is discharged by this contract's decision but NOT by any test in this repository.** jsdom
performs no layout. #29 must be re-verified on a device and only then marked fixed — see
[§ Backstops](#backstops-to-register-in-windowsmd).

### The documented escape

D-03's rejected sibling was **"drop `Best · N` from Title"**, and that is the escape rather than
something a future author invents. Dropping row 2 removes `24` fixed and `24` scaling: Title
becomes `F = 212`, `S = 208`, `H(1) = 420`, ceiling **1.581**. **It buys a whole extra row at any
plausible cap.** The Title rows in the order they would go:

1. `Best · {n}` (row 2) — D-03's named sibling. The campaign best is also on `SelectScreen`, one
   tap behind the Campaign entry, so it is the only Title row that is not the sole surface for its
   value.
2. The `Statistics` entry (row 6) — its screen is reachable from nowhere else, so this is a real
   loss, not a relocation.
3. Nothing else. Rows 1 and 3–5 are the brand and the three modes, which are D-01 and the screen's
   whole purpose.

## Spacing Scale

Declared values (multiples of 4). These govern the **React shell chrome** — never the 360×640
virtual playfield units. **Phase 14 adds no token and changes no shipped value.**

| Token | Value | Usage in this phase |
|-------|-------|---------------------|
| xs | **4px** | `gap` between the seven `By mode` table rows (S2); `marginTop` between an achievement name and its description (S3) |
| sm | **8px** | `gap` between the three lifetime rows (S2); `marginBottom` of the `By mode` section label; `marginTop` of the Title `Achievements` entry; `content` `paddingTop` (S2, S3) |
| md | **16px** | `marginTop` between mode entries (S1); `gap` between achievement entries (S3); mode-entry `paddingHorizontal`; the label↔meta row gap |
| lg | **24px** | Screen `paddingHorizontal` on all three screens (shipped); `marginTop` of `Best · {n}`, `Campaign`, `Statistics` (S1); every heading and section `marginTop` (S2, S3); `paddingBottom` at the end of the S3 scroll content |
| xl | 32px | (inherited — `SelectScreen` heading / list margins, untouched) |
| 2xl | 48px | (inherited — HUD strip content height, untouched) |
| 3xl | 64px | **No longer used anywhere.** It was the shipped `playButton.marginTop` on Title; row 3's `marginTop` is `lg` in the budget above. Kept in the scale as inherited, with no consumer |

**Exceptions:**

- **44×44 pt minimum touch target** (inherited, `06-UI-SPEC.md`). Every control on all three
  screens meets or exceeds it: filled mode entries compute to **48** (`12 + 24 + 12`), outlined
  secondary entries and `Back` to **46** (`12 + 20 + 12 + 1 + 1`). `minHeight: 44` is retained as a
  backstop on each and **never binds**.
- **The Brand row's 48 pt `lineHeight`** is a type value, not a spacing token, and the row costs
  two of them at 320 pt (see the correction above).

**Layout rules:**

- **Title never scrolls** (D-03). Not a `ScrollView`, not a `FlatList`, not `contentContainerStyle`.
- **Statistics never scrolls.** It fits at 458 / 548 and at 522.4 / 548 at the cap. If a future row
  breaks that, the remedy is the escape order in § S2 — **not** a scroll view.
- **Achievements scrolls, with `Back` and the heading in a fixed header outside the scroll view.**
  No sticky section headers, no floating affordance, no scroll indicator styling, no
  pull-to-refresh: the data is read once at mount.
- **Do not** shrink any padding, touch target, type size or gap to buy vertical room on any of the
  three screens. `12-UI-SPEC.md` § Layout rules forbids all four by name. The sanctioned levers
  are the per-screen row counts and escape orders above, and nothing else.
- **No new column.** Every row on every screen is a single label, optionally with one
  right-aligned meta on the same line (`flexDirection: 'row'`, `justifyContent: 'space-between'` —
  the shipped `SelectScreen.row` shape).
- At a 320 pt-wide viewport the zero left/right insets (measured) make `paddingHorizontal: 24` the
  only side margin, giving a **272 pt** text box on all three screens, and **240 pt** inside a
  filled mode entry (`272 − 16 × 2`).

| Label | 14px | 400 | 1.4 (20px) | Secondary-entry labels (`Statistics`, `Achievements`); `Back`; every right-aligned meta; the `By mode` section label; achievement descriptions and state markers |

**Sizes declared: exactly 4** (48 / 20 / 16 / 14). **Weights declared: exactly 2** (400, 600).
Body-emphasis is the existing Body size at the existing 600 weight, not a fifth size.

**Exceptions:** none new. `12-UI-SPEC.md`'s single exception — the 12 px `__DEV__` dev-row label,
fenced to development affordances and forbidden on any production surface — stands unextended.
This phase **deletes** two `__DEV__` controls and adds none.

**Character budgets, computed from the measured font metric.** SpaceMono is monospaced at 0.612 em
(`unitsPerEm` 1000, every `hmtx` advance 612, parsed from the shipped asset). #16's discharge
measured the real advance as slightly **narrower** than 0.612, so every budget below is
conservative — **and that margin is small, so no budget here is widened on the strength of it.**

| Box | Size | Advance | Characters |
|---|---|---|---|
| 272 pt screen text box | Body 16 | 9.792 | **27** |
| 272 pt screen text box | Label 14 | 8.568 | **31** |
| 240 pt filled mode-entry box | Body 16 | 9.792 | **24** |
| 240 pt filled mode-entry box | Label 14 | 8.568 | **28** |

**`numberOfLines={1}` is contract on:** every mode-entry label, every mode-entry meta, every
secondary-entry label and meta, every lifetime row label and value, and every `By mode` row label
and meta. It converts an authoring or magnitude mistake from *"a control is pushed off the bottom
of the screen"* into *"a value is visibly truncated"*, which is the strictly better failure —
`13-UI-SPEC.md`'s argument for the same device on the unlock lines.

**`numberOfLines` is deliberately ABSENT on achievement descriptions.** They **must** wrap: D-08
requires every entry to show its condition, and a truncated condition is not shown. The
Achievements screen scrolls, so a description growing from 2 lines to 3 costs scroll length rather
than a clipped control. This is the one place in this contract where wrapping is the correct
behaviour and truncation would be the defect.

### Three colour fences, stated as prohibitions because all three are live temptations

**1. `#6B7280` (Muted) may not appear on any of the three screens.** Computed by the WCAG 2.x
relative-luminance formula: **`#6B7280` on `#1a1a2e` is 3.53:1** — it **fails AA** for normal text
(4.5:1) and clears only the 3:1 large-text threshold. `SelectScreen` uses it today for the locked
row, and `14-CONTEXT.md` § Reusable Assets names that row *"the closest analog for both new
screens' list bodies."* **It is the right analog for the layout and the wrong one for the colour.**
Reusing it for a locked achievement's description would put D-08's whole point — *every entry shows
its condition* — below AA. `SelectScreen` itself is out of scope and unchanged; the observation is
routed to a window rather than a change.

**2. `#F2CC8F` (the record slot) may not appear on the Achievements screen.** `13-UI-SPEC.md`
fenced it on an argument that is semantic, not layout-driven: *"An achievement is not a record — it
is a threshold that was crossed once and never un-crosses (D-17)."* The layout half of that fence
(gold arguing with `New Record` on one panel) does not arise here, but the semantic half carries
unchanged, so gold is out. An unlocked entry is **not** marked by a colour.

**3. `#E85D5D` (destructive) may not appear on any of the three screens.** `12-UI-SPEC.md`
extended it to exactly one element, the streak-ended line, on an explicitly semantic argument.
**D-07 forbids Title from saying anything about a broken streak**, and nothing on Statistics or
Achievements is a loss: a locked achievement is an unmet goal, and a zero counter is a fresh
install.

### So how is locked / unlocked distinguished? By weight and by a word.

| State | Name | State marker | Description |
|---|---|---|---|
| Locked | Body 16 / **400** / `#FFFFFF` | `Locked` — Label 14 / 400 / `#FFFFFF` | Label 14 / 400 / `#FFFFFF` |

**Everything readable is `#FFFFFF` at 17.06:1, in every state.** The state is carried by the

**Never use accent for:** a trophy / medal / star / lock glyph, a rarity tint, a per-tier colour

## Copywriting Contract

Exact strings. `·` is U+00B7 MIDDLE DOT, matching every shipped metric line. Every string is a
fixed English literal plus an integer or an authored catalog string. **There is no user input and
no i18n path in this phase.**

**No thousands separators anywhere.** `Bricks broken · 1234567`, not `1,234,567`. Every shipped
metric line renders a bare integer (`Score · {score}`, `Streak · {streak}`); a separator would be a
new formatting rule, would widen every value against the budgets above, and would be the only
locale-dependent string in the app.

#### D-05's string is rendered as a label and a meta, not as one `Text`, and here is the arithmetic

D-05 locks the content — *`Daily` when today is unplayed; `Daily · done · Streak {n}` once played.*
**The literal single-`Text` form does not fit at 320 pt.** Inside a filled mode entry the text box

| Streak | String | Chars | Width | Fits 240 |
|---|---|---|---|---|
| `7` | `Daily · done · Streak 7` | 23 | 225.2 | ✅ |
| `12` | `Daily · done · Streak 12` | 24 | 235.0 | ✅ |
| **`365`** | `Daily · done · Streak 365` | 25 | **244.8** | ❌ over by 4.8 |
| `1234` | `Daily · done · Streak 1234` | 26 | 254.6 | ❌ |
| `36525` | `Daily · done · Streak 36525` | 27 | 264.4 | ❌ |

**A three-digit streak is not exotic — it is the aspirational player**, and phase 12 measured a
real streak of 450 (`longestStreak` 450 over 450 consecutive closes), with
`DAILY_STREAK_WALK_CAP = 36525` as the tamper fence. The one-line literal would break for exactly
the player it is meant to reward.

**The shipped form:** label `Daily` at Body 16 (49.0 pt), a 16 pt `md` gap, meta

| Streak | Total width in a 240 pt box |
|---|---|
| `7` | 193.5 ✅ |
| `365` | 210.6 ✅ |

one between `Daily` and `done`, and the accessibility label speaks the whole thing as one sentence

not "restore" the literal and silently reintroduce the overflow.

### Achievements (S3)

| Element | Copy | Source |
|---|---|---|
| Back | `Back` | (shipped, verbatim) |
| Heading | `Achievements` | — |
| Entry name | `{name}` | `ACHIEVEMENT_CATALOG[i].name` — **never a stored string** (T-13-01's mitigation) |
| Entry description | `{description}` | `ACHIEVEMENT_CATALOG[i].description`, rendered in **both** states (D-08) |
| State marker, locked | `Locked` | the stored unlocked set does not hold this id |

**Why `New` and not `Unlocked · new`.** The three markers share one right-aligned slot beside the
name. Computed against the worst-case name (`Flawless Clear`, 14 chars, 137.1 pt at Body 16) in a
272 pt box with a 16 pt gap: `Unlocked · new` (14 chars, 119.9 pt) totals **273.0 pt and overflows

221.6, with 50 pt of spare.

**`New` is a mark, not a notification** (D-11 / § Specifics). It is a word in a row of a list. There
is no toast, no modal, no dot, no count badge, and no mark on any **mode** entry. The `{n} new`
meta on Title sits on the **Achievements secondary entry** — the entry that leads to the thing
being marked — which is a signpost, not a notification on an unrelated control. D-05 rejected a
bare count for the daily; `{n} new` is never bare, because the label it qualifies names exactly
what is new.

**`new` is invariant.** `1 new`, `3 new`, `12 new` — no plural branch, no `s`. Widths at Label 14
in a 272 pt box: 161.7 / 161.7 / 170.2 pt.

**All twelve entries render, always, in catalog declaration order (D-10).** No grouping, no
section headers, no unlocked-first sort, no recency sort. The list never re-orders when an entry
unlocks, so a scroll position means the same thing on every visit — which is what makes the scroll
in § S3 acceptable.

| State | Treatment |
|---|---|

### Error states

**No error modal, no banner, no error copy anywhere** (inherited, `06-UI-SPEC.md`; restated in
`12-UI-SPEC.md`). Every failure degrades to a default, downward, silently.

| Failure | Behaviour | Copy |
|---|---|---|
| `getSnapshot()` fails on Statistics | Render `defaultTelemetryBlob()` — all zeros | none |
| `getSnapshot()` fails on Achievements | Render all twelve as `Locked` | none |
| `getSnapshot()` / `getBest()` fails on Title | `Best · 0`; `Daily` with no meta; `Achievements` with no meta | none |
| A stored achievement id the catalog does not know | **Dropped** — the entry never renders (D-14's read path, matching `sanitizeAchievementRecord`) | none |
| `telemetry` degraded by `sanitizeTelemetry` | The screens render the degraded (zeroed) values; campaign bests, stars, unlocks and the daily record are provably untouched | none |
| The seen-state write fails on Achievements exit | The marks **reappear** on the next open | none |

**Two named costs, accepted:**

- **A transient read failure makes an unlocked achievement read as `Locked`.** Unlike phase 12's
  daily read-failure rule, this one **writes nothing** and is fully recovered by reopening the
  screen, so the worse alternative (blocking the screen on a fault) buys nothing.
- **A failed seen-write re-shows the mark.** That is D-13's direction of harm, chosen deliberately:
  seeing `New` twice on an entry you have read is strictly better than never seeing it on an entry
  you have not.

### Destructive confirmation

**None, anywhere in this phase.** Nothing on any of the three screens deletes, resets, or
overwrites anything the player would want back.

- Entering Endless or Daily from Title shows **no** confirmation. D-07 of phase 12 says abandoning
  a daily does not close the date, so entering commits to nothing; a confirmation would claim a
  commitment that does not exist.
- Tapping `Daily` on an already-played day shows no confirmation — D-06 routes it to the stored
  result panel, which generates no board and writes nothing.
- **Opening the Achievements screen persists the seen-state** (D-12) and takes **no** confirmation.
  It is an additive v4 field recording that the player looked at a list; it destroys nothing, and
  D-17 makes an unlock one-way regardless.
- `Back` on either new screen is instant (RUN-03, inherited). No confirmation, no animation gate.

## Interaction Contract

### The router — where two screens join, and how SC-5 stays structural

`ShellPhase` widens to `'title' | 'select' | 'playing' | 'stats' | 'achievements'`.

**The two new branches are early returns ABOVE the final `PlayingHost` return in `GameHost`,
exactly as `'select'` is.** That is how SC-5 and `N-UI-02` are satisfied — structurally, not by a
check:

- Neither new screen mounts `PlayingHost`, `GameScreen`, a Skia `Canvas`, or any `useFrameCallback`
  / worklet. **There is nowhere for a run to live behind them.**
- D-04 keeps `onMenu={() => setShellPhase('title')}` unchanged: **one return path for all three
  modes**, so the shell remembers no entry route and **no new shell state exists for a run to
  survive in.**
- `Back` on both new screens returns to `'title'`, and only to `'title'`. Neither screen is
  reachable from `'playing'`, so no navigation edge exists between a run and either screen.

**The soak and CERT harnesses stay Title↔Playing only.** `GameHost`'s phase-11 D-01 note —
*"only `'title'` | `'playing'` — never `'select'`"* — extends verbatim to the two new phases:
`runCycle` must never set `'stats'` or `'achievements'`, and `CERT_HARNESS` must still open
directly on `'playing'`. A meta screen in the soak loop would measure the wrong thing.

### Reads happen once per screen entry, never per frame (N-STAT-03 / SC-2)

| Screen | Read | Pattern |
|---|---|---|
| Title | `getBest()` **plus** the daily record **plus** the unseen-unlock count | Extend the **shipped** effect, which is already gated `if (shellPhase !== 'title') return;`. One effect, one entry, three values |
| Statistics | one `getSnapshot()` on mount | `SelectScreen`'s shipped mount effect, verbatim in shape (deep clone, `cancelled` guard, `.catch` → defaults) |
| Achievements | one `getSnapshot()` on mount, plus **one** seen-state write | same, plus the write below |

**No screen re-reads on focus, on an interval, on a timer, or per frame.** There is no live
interval anywhere in this phase — the countdown was considered for D-05 and rejected precisely
because it needs one, and phase 12 took care to keep that interval scoped to the daily panel being
open. `N-STAT-03` is satisfied by the read pattern, not by a memo.

### The seen-mark: what the screen renders, and when it writes (D-11 / D-12)

**The Achievements screen snapshots the unseen set at mount and renders from that snapshot. The
rendered marks do not change while the screen is open.**

1. On mount, read the snapshot. Compute the unseen set: unlocked ids not yet marked seen.
2. Render. Entries in that set show `New`.
3. **Write the seen-state once, on mount.** Opening the screen is the "seen" event (D-12).
4. **Do not re-render from the write.** If the marks cleared as the player looked at them, D-11's
   mark would be invisible in the one case it exists for.
5. On return to Title, the unseen count is 0 and the `Achievements` entry shows no meta.

D-12's other half is already shipped: `recordRunEnd` returns the delta and the result panels
render it, so those entries have genuinely been seen and are marked at that moment. **The screen
marks everything else** — in practice, almost always an abandoned run, which is exactly the
7-of-12 case `WINDOWS.md` #35 quantified.

**Unlocks that predate the field are seen (D-13).** No migration, no version bump — an additive v4
field, following phase 13's D-13 shape.

### Both new screens are read-only surfaces with exactly one control

`Back`. Nothing else on either screen is tappable, long-pressable, swipeable or selectable. No
per-entry detail (D-09), no drill-down (D-15), no sort control (D-10 makes order contract), no
filter, no share.

### What jsdom cannot observe

The project's UI tests run under `jsdom` + `@testing-library/react`, which **performs no layout and
supplies no safe-area insets.** It cannot report wrapping, clipping, truncation, overlap, scroll
extent or fit. **Every height, width, line-count, visible-entry-count and character-budget claim
above is a `backstop` routed to a human**, never something a `render()` assertion can close. A
passing `npm test` is not evidence that any of these three screens fits, and must never be recorded
as one.

### What jsdom can observe, and must

The limit is layout, and only layout. These are `explicit` and each owes a case:

- `MAX_FONT_SCALE` is `1.2`, and every `Text` in the twelve enumerated files passes it — asserted
