<appstate_conflict_decision>
## DECIDED: Option A, in the form that adds no second subscription

`12-PATTERNS.md § The One Conflict` tabled two options without choosing. **The plan chooses
Option A**, threaded through the existing single call site rather than as a second subscription:

1. `src/runtime/appStatePause.ts` gains an **optional** `onForeground?: () => void`. The `active`
   branch calls that callback and nothing else.
2. `src/runtime/useGameLoop.ts` gains an optional `onOsForeground?: () => void` option beside the
   shipped `onOsPause?: () => void` at `useGameLoop.ts:232`, and passes it straight through to
   the one existing `subscribeAppStateAutoPause` call at `useGameLoop.ts:768`.
3. `app/_components/PlayingHost.tsx` supplies it at the `useGameLoop({ … })` call site
   (`PlayingHost.tsx:579-590`), where `onOsPause` is already threaded in at `:586`.

**Why, against Option B.** Option B puts a second `AppState.addEventListener` in the app. The
repository has exactly one today — a grep over `src/` and `app/` returns a single occurrence, in
`appStatePause.ts` — and one call site for the helper that wraps it. Two subscriptions with
independent lifetimes means no single place a reader can see what the app does on foreground,
which is precisely the "two renderers for one truth" shape `11-UI-SPEC.md` was written to repair.
Option A keeps one subscription, one helper and one foreground contract.

**Why the never-auto-resume invariant survives.** `appStatePause.ts` asserts the absent `active`
branch twice — JSDoc at `:11` and inline at `:24`.

**Which decision that invariant actually is — resolved, because the shipped comment is ambiguous.**
The invariant is *never auto-resume physics on foreground*. Its phase-independent identifiers are
requirement **PLT-01** (`.planning/REQUIREMENTS.md:48` — "app auto-pauses on OS
background/interruption and resumes with a countdown (no physics catch-up spiral)") and threat
**T-03-03** ("AppState freeze, no auto-resume"). The shipped JSDoc at `:8` cites the triad
`PLT-01 / D-15 / T-03-03`, and that `D-15` is **Phase 3's** D-15 (`03-CONTEXT.md:43`: "require an
explicit tap (Resume control), then a 3-second countdown … **Never auto-resume gameplay** after an
OS interruption"). It is **not** this phase's D-15, which is the bounded daily-history window and
has no bearing on the foreground branch at all. An executor holding `12-CONTEXT.md` open would read
the bare id wrongly, so every reference to this invariant in this plan names PLT-01 and T-03-03,
and says "Phase 3's D-15" whenever the inherited id is meant.

Option A preserves the invariant in fact: the `active` branch
touches no physics handle, no active flag, no UI phase and no accumulator. It becomes **stronger**
than a comment, because `useGameLoop` decides what is passed and the helper cannot reach physics
on its own. Both comments are rewritten to state the invariant rather than the implementation
detail that used to carry it: on `active`, invoke only the foreground notification callback; never
resume physics, never set the active flag, never touch the UI phase or the accumulator — the frame
loop stays frozen until Resume and its countdown.

**Effect on the approved UI-SPEC rule 4 — an explicit, narrow amendment.** Rule 4 reads "on mount,
on every `AppState` → `active`, and on a 60-second interval". It is **honoured as written in every
dev and production build**. It is **amended for one case**: `useGameLoop`'s subscription is skipped
entirely under the cert-metrics harness (`useGameLoop.ts:765-767` returns before subscribing), so
under that harness the foreground trigger does not fire while mount and the 60-second interval
still do. The cost is bounded and acceptable on the UI-SPEC's own reasoning — the countdown is
decoration and never a gate (rule 1), playability is evaluated only by D-01, and the cert harness
is a development instrument with no player on the other side. Recording the amendment here rather
than letting an executor discover it is the whole point of deciding this at plan time.
</appstate_conflict_decision>
