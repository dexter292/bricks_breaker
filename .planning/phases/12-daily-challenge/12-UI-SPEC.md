# Phase 12 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

## What this contract covers, and what it deliberately does not

`12-CONTEXT.md` D-01..D-17 are **LOCKED** and are not re-opened here. This contract pins the
three UI surfaces that follow from them, plus the entry point:

| Surface | Exists because | Locked input |
|---------|----------------|--------------|
| **S1** `__DEV__` `Daily` entry control | Phase 14 owns the real Title entry; this phase needs a way in | D-05 (Phase 11), CONTEXT § Discretion |
| **S2** Daily Result panel — **one** panel serving both "just finished" and "re-opened today" | SC-2: re-opening on the same date shows the stored result rather than regenerating | D-01, D-02, D-06, D-07, D-12 |
| **S3** Streak block inside S2 — current, best-ever, total, and the streak-ended line | D-13/D-14/D-16/D-17; the roadmap goal's "a streak they would be annoyed to lose" | D-13..D-17 |
| **S4** Countdown line inside S2 | CONTEXT D-07's chosen answer: "result + countdown to tomorrow" | § Clock policy below |

**Explicit non-goals (Phase 14, `N-UI-01` / `N-UI-02`):**

- Any **production** entry point into daily. The `__DEV__` Pressable specified below is the
  Phase 11 D-05 pattern and is **deleted by Phase 14**. It must not appear in a production build.
- A **permanent** streak surface on Title or a stats screen. `N-UI-01` explicitly owns "the daily
  entry shows whether today has been played" — that is Phase 14's sentence, not this phase's.
- Any **date picker, calendar grid, or history list.** This phase renders exactly one date: the
  current local one. There is no route to a past date, so there is no list surface anywhere here.
- Achievements over daily play (Phase 13).

**Continuity:** reuses `11-UI-SPEC.md`, which reuses `06-UI-SPEC.md` (shell/HUD/overlay chrome),
which reuses `03-UI-SPEC.md` (tokens, gesture/UI separation) and is extended by `D1-UI-SPEC.md`
(juice). **Phase 12 introduces zero new colors, zero new type sizes, zero new spacing tokens and
zero new packages.** Every numeric value in this document was read out of the shipped source — see
[Measurement Provenance](#measurement-provenance) for what was measured, what was computed, and
what an implementer still has to verify.

## Typography

Shell / chrome only. Skia gameplay entities unchanged. `SpaceMono` is the only family — do not
introduce a second.

| Role | Size | Weight | Line Height | Usage in this phase |
|------|------|--------|-------------|---------------------|
| Body | 16px | 400 | 1.5 (24px) | Daily Result body line; **every** daily metric line (`Daily ·`, `Score ·`, `Streak ·`, `Best streak ·`, `Days played ·`, the streak-ended line, the countdown line); `Retry` CTA label |
| Label | 14px | 400 | 1.4 (20px) | HUD strip metrics; `Pause`; `Menu` label; the record-slot badge label |
| Heading | 20px | 600 | 1.2 (24px) | Daily Result headings: `Win`, `Lose`, `Daily` (the board-failure variant); `Paused` |
| Display | 48px | 600 | 1.0 | `Resume` countdown numerals — **untouched** by daily, and explicitly **not** the type used for the tomorrow countdown (see below) |

**Weights declared (exactly 2):** 400 (regular) + 600 (semibold).

**Exception:**

| Exception | Value | Reason |
|-----------|-------|--------|
| `__DEV__` dev row label | 12px / 16px line-height, weight 400 | `styles.devSwitchLabel` — development affordances only (`Lv`, tier, `Cert WC`, `Endless`, `W{n}`, **`Daily`**, `Crash`). **The tomorrow countdown is Body, not Display.** A 48px numeral would make "when the next board
arrives" the visual anchor of a panel whose subject is *what you did today*. The countdown is the
last line before the CTA precisely so it reads as a footnote. This is a deliberate rejection of the
timer-as-hero pattern.

Daily adds **no new size and no new weight** — every new line is Body, the one new heading string
reuses the existing Heading token.

## Color

60 / 30 / 10 for the shell + play composition. Flat solids. **Daily introduces no new hex value.**

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `#1a1a2e` (`FIELD_NAVY`) | Playfield fill behind the daily board; label on the record-slot badge |
| Secondary (30%) | `#000000` letterbox + scrim `rgba(0,0,0,0.6)`; panel `#12121f`; HUD strip `rgba(18,18,31,0.8)` | Letterbox bars; Daily Result / Pause scrim; panel fill; HUD backing; dev button fill |
| Accent (10%) | `#FFFFFF` (`BALL_PADDLE`) | Ball/paddle; `Retry` fill; `Menu` outline + label; HUD metric text; the `Win` and `Daily` headings; **all** daily metric lines except the streak-ended one; the countdown line |
| Destructive | `#E85D5D` | The `Lose` heading **and** the streak-ended line — see the extension note below |
| Record slot | `#F2CC8F` (`BRICK_HP1`) | The `Best streak ever` badge fill **only** |
| Muted | `#6B7280` (`BRICK_UNBREAKABLE`) | Dev button borders only. **Never** for a daily number the player is meant to read |

**Accent (`#FFFFFF`) reserved for:**

1. Ball / paddle silhouettes (unchanged)
2. Primary CTA fill — `Retry`, which in daily renders **only** while the date is still open
3. `Menu` secondary outline (1px border + label) on the `#12121f` panel
4. HUD strip metric text and the `Pause` outline control
5. Daily Result body, the `Daily ·` / `Score ·` / `Streak ·` / `Best streak ·` / `Days played ·`
   lines, and the countdown line
6. `Resume` countdown numerals

**Never use accent for:** brick fills, letterbox, scrim, ornamental borders, a streak flame/flair
graphic, a progress ring around the countdown, ads/IAP/login chrome (forbidden), or the Phase 1
cliff-ramp cyan `#00ffaa` outside the `__DEV__` perf overlay.

**Destructive extension — the one palette change in this phase.** `11-UI-SPEC.md` scoped `#E85D5D`
to "the `Lose` heading **only**". This contract extends it to exactly one more element: the
streak-ended line. The justification is semantic, not decorative — D-17 exists because the loss is
the point of the feature, and a loss statement rendered in the same accent white as
`Days played · 45` states it without meaning it. **This is the only extension; no other daily
element may take `#E85D5D`,** and in particular the `Streak · 1` line that follows a break stays
accent white (the new streak is not itself a loss).

A `Win` heading and a red streak-ended line **can and must** co-render: winning today after a
two-week gap is exactly that situation, and suppressing either one would misreport it.

**Contrast, computed (not device-measured) from the two hex values by the standard WCAG 2.x
relative-luminance formula, 2026-09-27:**

| Pair | Ratio | Verdict |
|------|-------|---------|
| `#E85D5D` on panel `#12121f` | **5.44:1** | passes AA normal text (≥4.5), fails AAA (≥7) |
| `#FFFFFF` on panel `#12121f` | 18.55:1 | passes AAA |
| `#1a1a2e` on badge `#F2CC8F` | 11.22:1 | passes AAA |
| `#6B7280` on panel `#12121f` | 3.84:1 | **fails AA normal text** — which is why Muted is fenced to dev borders and never to a readable daily number |

The 5.44:1 figure is the reason the streak-ended line is allowed to be Body 400 rather than needing
a weight bump: it clears AA at 16px as-is. It is a computation over hex values, **not** a
measurement on a rendered device — an implementer changing either hex must recompute.

## Copywriting Contract

Exact strings. `·` is U+00B7 MIDDLE DOT, matching every shipped metric line. Every string below is
a fixed English literal plus integers — there is no user input and no i18n path in this phase.

### Daily Result panel — line order is contract

Heading → body → `Daily ·` → `Score ·` → `Streak ·` → `Best streak ·` → `Days played ·` →
streak-ended line → badge → countdown → `Menu`.

The order is: *what happened* → *to which date* → *what today scored* → *the streak block* → *what
was lost* → *what was gained* → *when the next one comes* → *the way out*.

| # | Element | Copy | Renders when |
|---|---------|------|--------------|
| 1 | Heading (win) | `Win` | the stored outcome is a cleared board (D-10) |
| 1 | Heading (lose) | `Lose` | the stored outcome is out-of-lives (D-10) — `#E85D5D` |
| 2 | Body (win) | `All clear` | with the `Win` heading |
| 2 | Body (lose) | `Out of lives` | with the `Lose` heading |
| 3 | Date | `Daily · {YYYY-MM-DD}` | always |
| 4 | Score | `Score · {n}` | always |
| 5 | Current streak | `Streak · {n}` | always; `n ≥ 1` is guaranteed (see zero states) |
| 6 | Best ever | `Best streak · {n}` | always |
| 7 | Total | `Days played · {n}` | always — this line exists so `totalDaysPlayed` (D-16) has a reader |
| 8 | Streak ended | `Your {n}-day streak ended` | only under the derivation rule below — `#E85D5D` |
| 9 | Record badge | `Best streak ever` | only under the badge rule below |
| 10 | Countdown | `New board in {h}h {m}m` / `New board in {m}m` / `New board in under a minute` | per the countdown rule below |
| 11 | Primary CTA | `Menu` | always, and it is the **only** control on a closed date |

**No `Best · {n}` score line, ever.** With one attempt per date (D-06) there is no per-date score
to beat, and D-16 stores no lifetime best *score* for daily — only `longestStreak` and
`totalDaysPlayed`. Rendering a `Best ·` line would require inventing storage this phase did not
decide on, and reading the campaign or endless watermark to fill it would break SC-5 outright.
**The absence is contract.**

**No star row, ever** (D-12). **No `Retry` on a closed date** (D-06 — see the open/closed rule in
the Interaction Contract). **No `Next`** — daily has no next level.

**The date is rendered verbatim from the stored key.** The copy above assumes the key is ISO-8601
local `YYYY-MM-DD`. The planner retains CONTEXT's discretion over the stored key format, but this
contract constrains it to a form that is renderable **verbatim with no formatting step** — a
locale-formatted date is a second representation that can disagree with the key the board was
derived from, and SC-1's whole claim is that those are the same thing. ISO also sorts, which is
what D-14's "walk over the sorted set of stored dates" needs anyway.

### The streak-ended line — exact derivation (D-17)

Let `D` be the date shown, and `prev` the greatest stored date strictly before `D`.

| Case | Line |
|------|------|
| `prev` is `D − 1 day` | **omit** — the streak continued |
| `prev` does not exist | **omit** — first date ever recorded |
| `prev < D − 1 day`, ended length derivable and `≥ 2` | `Your {endedLength}-day streak ended` |
| `prev < D − 1 day`, ended length is `1` | **omit** — "Your 1-day streak ended" is not a loss worth stating |
| `prev < D − 1 day`, ended length **not derivable** | **omit** — see below |

`endedLength` is the count of consecutive stored dates ending at `prev`, walked backwards over the
bounded window (D-15).

**Not derivable means: the backward walk reached the oldest date still in the trimmed window while
still consecutive.** The true length is then unknown, and the line must be omitted. **Never
substitute `longestStreak`** — D-16's scalar may belong to an entirely different, earlier run, and
printing it here would state a number that was never the streak that just ended. A silent omission
is the honest failure mode; a confident wrong number is not.

The `≥ 2` floor also removes the only pluralization branch in the phase: at `n ≥ 2`, `{n}-day` is
always correct English. There is no `1-day` string to get wrong.

This line renders **only on the first date of a new streak**, and disappears once the next
consecutive date closes. That is intended: it reports a transition, not a status.

### The record badge rule

| Rule | Value |
|------|-------|
| Copy | `Best streak ever` |
| Fires iff | `streak ≥ 2` **and** `streak === longestStreak` |
| Style | the existing `styles.badge` / `styles.badgeLabel` — `#F2CC8F` fill, `#1a1a2e` label, Label 14px |

**Why `===` and not `>`.** The panel is a pure function of the **stored** record (see the
Interaction Contract), and by the time it renders, `longestStreak` has already absorbed this date's
close — so `streak > longestStreak` is false and the badge would appear at the end of a run and
then vanish on re-open the same day. `===` is stable across re-opens and derivable at render with
no extra stored field.

**Why the copy is `Best streak ever` and not `New Record`.** `===` is also true on a *tie* with an
earlier run's longest, where `New Record` would be a false statement. `Best streak ever` is true in
both the exceed and the tie case. `#F2CC8F` remains the single record slot; daily's badge and
endless's `New Record` badge live on different overlays and can never co-render.

**Why `≥ 2`.** A first-ever daily makes `streak === longestStreak === 1`; celebrating that is
noise. From day 2 onward the badge appears on every day the player extends their best-ever run,
which is exactly the "annoyed to lose" pressure the roadmap goal asks for.

### The countdown line

| Remaining until next local midnight | Copy |
|---|---|
| `≥ 1h` | `New board in {h}h {m}m` — both **floored** |
| `1m ≤ r < 1h` | `New board in {m}m` — floored |
| `0 < r < 1m` | `New board in under a minute` |
| `≤ 0`, `NaN`, or non-finite | **omit the line** and re-derive the local date key (see Clock policy) |

Floored, not rounded: at 23h 59m 30s remaining, a ceiling would print `24h 0m`, which is longer
than a day and reads as a bug.

### Board-failure variant (the daily date stays OPEN)

When today's board cannot be generated, the date **must not close** — the player never played it.

| Element | Copy |
|---------|------|
| Heading | `Daily` — accent white, **not** the `Lose` red. Nothing was lost |
| Body | `Today's board could not be built — tap Retry` |
| Lines rendered | `Daily · {YYYY-MM-DD}`, `Streak · {n}`, `Best streak · {n}` — still true, still derived from storage |
| Lines suppressed | `Score ·`, `Days played ·`, the streak-ended line, the badge, the countdown — all of them describe a *closed* date, and this date is open |
| Controls | `Retry` (primary, accent-white fill) **then** `Menu` |

`Retry` is legitimate here and only here on a result-shaped panel, because the date is still open —
which is the same single rule (D-01) that forbids it after a close. The wording deliberately
mirrors Phase 11's shipped `Wave 1 could not be built — tap Retry`.

**Never render `LevelErrorOverlay` for a daily board failure.** It has no controls and would trap
the player with no exit — the same rule `11-UI-SPEC.md` set for a wave-build failure.

### Storage-failure copy and policy

| Failure | Behaviour | Copy |
|---------|-----------|------|
| Snapshot **read** fails or the daily record is unreadable | Treat the date as **having no stored result** → playable | none — no error modal, no banner |
| Snapshot **write** fails when the date closes | Render the Daily Result panel from the in-memory record so the player still sees their result | none — no error modal |
| `daily` telemetry / record degraded by `sanitizeTelemetry` | Panel renders the degraded (zeroed) values; campaign bests, stars, unlocks and endless records are provably untouched | none |

**The named cost of the read-failure rule:** treating an unreadable record as "no result" means a
transient storage error can hand a player a second attempt at the day. That is accepted, on the
same reasoning as D-08's accepted practice hole — the alternative (treat unreadable as closed)
locks a player out of their day on a transient fault, which is the strictly worse failure. Named
here so a later round finds a decision rather than a defect.

**No error modal anywhere in this phase** (inherited, `06-UI-SPEC.md`).

### Destructive confirmation

**None, anywhere in this phase.**

- Entering the daily board shows **no** "you only get one attempt" confirmation. D-07 says
  abandoning does not close the date, so entering commits to nothing. A confirmation would claim a
  commitment that does not exist — it would be a false dialog.
- Pause → `Retry` during a live daily run shows no confirmation. It restarts **the same board**
  (D-08) and the date stays open; nothing is destroyed.
- `Retry` and `Menu` stay instant (RUN-03, inherited).

### Empty and zero states

| State | Reachable? |
|-------|-----------|
| `Streak · 0` | **unreachable on this panel** — the panel only renders for a date that has a result, and a closed date makes the current streak `≥ 1` by construction |
| `Best streak · 0` | unreachable for the same reason |
| `Days played · 0` | unreachable for the same reason |
| A "no daily played yet" empty panel | **does not exist this phase** — with no Title entry and no history list, the only way to reach the panel is through a date that has a result. The zero state is `N-UI-01`'s, in Phase 14 |
| A list / collection empty state | **does not exist** — this phase ships no list, no calendar and no history view |

### Accessibility labels

| Control / readout | `accessibilityLabel` | Note |
|---|---|---|
| `__DEV__` `Daily` button | `Open today's daily challenge` | new |

## Interaction Contract

### The panel is a pure function of the stored daily record

**Required.** When a daily run closes, the result is **written first**, and the panel is then
rendered **from the stored record** — the same render path that a re-open on the same date takes.

This is the direct implementation of SC-2, and it is chosen over a "just-finished" view that reads
in-memory run state because that shape produces two renderers for one truth, which is precisely the
defect family `11-UI-SPEC.md` was written to repair (endless Results showing a campaign number). If
the two views can disagree, one of them is wrong and no test will tell you which.

Consequences that are part of the contract:

- The panel takes **only** daily-derived values as props. It must **not** accept or read
  `previousBestRef`, `store.getBestForLevel(...)`, `telemetry.endless`, or `stars` — SC-5 at the
  prop signature, where it is checkable by reading the type rather than by tracing a branch.
- Writing a daily result must **never** touch `bestByLevel`, `unlocked`, `telemetry.endless`, or
  the campaign PB ref. (`memoryStore.ts` and `asyncStorageStore.ts` already carry the "endless **or
  daily**" guard — this phase **verifies** that rather than assuming it, per `12-CONTEXT.md`
  § Established Patterns.)
- The panel takes **`now` as an injected value**, never calling `Date.now()` inside its own render.
  Without this, the 23h-59m case, the sub-minute case and the rollover case are not testable
  deterministically, and the countdown becomes the one line in the phase no test can pin.

### A new component — `ResultOverlay` is NOT widened to `'daily'`

**Required.** Ship a separate `DailyResultOverlay`. `ResultOverlay`'s `mode` prop stays
`'campaign' | 'endless'` and is never widened.

The reason is measured, not stylistic: `ResultOverlay` already carries `best`, `wave`, `bestWave`,
`waveBuildFailedWave`, `stars`, `onNext` and `isNewRecord`, several mutually exclusive by mode. A
third mode that needs five new lines, no `Retry` on close, a different badge rule and a live timer
would make every prop conditionally meaningless — the exact shape that let a campaign number render
on an endless panel.

`DailyResultOverlay` must reuse the chrome values **verbatim**. Extracting them into a shared
stylesheet module is permitted but not required; what **is** required is that each value below
matches, exactly:

| Style | Values (read from `ResultOverlay.tsx`, 2026-09-27) |
|---|---|
| `scrim` | `StyleSheet.absoluteFill`, `rgba(0,0,0,0.6)`, centered, safe-area padding on all four sides |
| `panel` | `#12121f`, `padding: 24`, `minWidth: 200`, `maxWidth: 320`, `alignItems: 'stretch'` |
| `heading` | `#FFFFFF`, SpaceMono, 20px, `600`, lineHeight 24, centered, `marginBottom: 16` |
| `loseHeading` | `#E85D5D` |
| `body` | `#FFFFFF`, SpaceMono, 16px, `400`, lineHeight 24, centered, `marginBottom: 16` |
| `metric` | `#FFFFFF`, SpaceMono, 16px, `400`, lineHeight 24, centered, `marginBottom: 8` |
| `badge` | `alignSelf: 'center'`, `#F2CC8F`, `padding: 4`, `marginBottom: 16` |
| `badgeLabel` | `#1a1a2e`, SpaceMono, 14px, `400`, lineHeight 20 |
| `button` (primary) | `minHeight/minWidth: 44`, `paddingHorizontal: 16`, `paddingVertical: 12`, centered, `#FFFFFF` |
| `buttonLabel` | `#1a1a2e`, SpaceMono, 16px, `400`, lineHeight 24 |
| `menuButton` | `minHeight/minWidth: 44`, `paddingHorizontal: 16`, `paddingVertical: 12`, centered, `#12121f`, `borderWidth: 1`, `borderColor: '#FFFFFF'` |

### Open vs closed — the one rule that governs every control

D-01 states the whole clock policy: **a date is playable iff it has no stored result.** The UI
expresses exactly that rule and adds nothing to it:

| Date state | `Retry` present? | Why |
|---|---|---|
| **Open** — in a live run (Pause overlay) | **yes** | restarting is possible; it re-runs the same board (D-08) |
| **Open** — board-failure variant | **yes** | nothing was recorded; a second generation attempt is legitimate |
| **Closed** — Daily Result panel | **no** | D-06: one attempt. The date is done; a control that cannot work must not render |

There is no disabled/greyed `Retry` anywhere. A control the rule forbids is **absent**, not
decorated — a greyed button invites a tap and then explains itself, which is a dialog in disguise.

### Run boundaries (daily)

| Trigger | Contract |
|---|---|
| `__DEV__` `Daily` pressed, today **open** | Derive the local date key → seed → `generate(dateKey, DAILY_DIFFICULTY)` → start a campaign-shaped run (D-10). No confirmation, no intro screen |
| `__DEV__` `Daily` pressed, today **closed** | Render the Daily Result panel from the stored record. **Do not** generate a board, do not start a run (D-02, SC-2) |
| Board cleared | Write the `win` result, **then** render the panel from the stored record |
| Lives → 0 | Write the `lose` result, **then** render the panel from the stored record |
| Pause → `Retry` during a live daily run | Record the in-flight run as `abandoned` first (D-09), then restart **the same date-derived board**. The date stays open |
| Pause → `Menu` during a live daily run | Record as `abandoned`, then Title. The date stays open (D-07) |
| `remountDevSession` / dev tier change during a daily run | Record as `abandoned`, then exit daily — same treatment Phase 11's controls received |
| App backgrounded mid-run | Existing AppState auto-pause, unchanged. Backgrounding is not abandoning and is not closing |

**Two anti-patterns, named because the adjacent Phase 11 code does exactly the opposite:**

1. **Daily `Retry` must never re-mint a seed.** `startEndlessRun()` re-mints `runSeedRef` on every
   Retry — correct for endless, and an outright SC-1 / N-DAILY-01 break here. The daily seed is a
   pure function of the date and nothing else.
2. **Daily must not take Phase 11's `WON` wave-advance intercept.** A cleared daily board **ends
   the run** (D-10). If the endless intercept is reached from daily, the board silently advances
   and the date never closes.

### Clock policy in the UI — resolving the countdown/D-01 tension

D-01..D-05 deliberately trust the clock for **one** question: *what local calendar date is it?* A
countdown trusts it for a **duration**. The resolution:

1. **The countdown is decoration and never a gate.** Nothing branches on it. Playability is
   evaluated only by D-01 — "does this local date have a stored result" — re-derived from a fresh
   local-date read on every render and on every foreground.
2. **It is derived, never accumulated.** Compute `nextLocalMidnight − now` from a single `Date`
   read each time it is displayed. No stored deadline, no elapsed-time accumulator, no
   `setInterval` tick that decrements a counter. A clock jump therefore changes the next computed
   value and can make nothing else go stale — there is no second piece of state to disagree.
3. **`nextLocalMidnight` is calendar arithmetic**, not `now + 86_400_000`: take the local date,
   add one day, set 00:00:00.000 local. Under DST a day is 23h or 25h and the displayed value
   simply reflects it — which is correct, because the *board* changes at local midnight too.
4. **Refresh cadence:** on mount, on every `AppState` → `active`, and on a 60-second interval.
   Minute granularity is the whole reason a 60s tick suffices; a per-second timer would buy a
   digit nobody reads and keep a timer alive behind a result panel.
5. **A non-positive or non-finite remainder is never displayed.** It means the local date has
   already rolled (or the clock moved). Re-derive the date key; if the new date has no stored
   result the panel is replaced by the playable entry state — the countdown never renders a
   negative duration and never "expires in place".
6. **A backwards clock jump changes only the countdown's number.** The stored date stays closed and
   read-only (D-02), and the panel keeps rendering the stored result. The countdown may briefly
   show a longer remainder; that is the honest display of what the device says the time is, and it
   grants the player nothing.

### Entry point — `__DEV__` only

`__DEV__` `Daily` Pressable in the existing dev row in `PlayingHost.tsx`, styled with the existing
`styles.devSwitch` / `styles.devSwitchLabel`, `hitSlop={8}`, visible label `Daily`,
`accessibilityLabel` `Open today's daily challenge`. Guarded by the existing
`typeof __DEV__ !== 'undefined' && __DEV__` expression so it **cannot** ship in a production build.
Phase 14 deletes it (`N-UI-01`).

| Rule | Contract |
|---|---|
| Position | Immediately **to the right of** `Endless`, keeping the two mode-entry buttons adjacent |
| New readout | **None.** No `D{n}` counterpart to `W{n}` — see below |
| Behaviour | One button, both date states. What it does is decided by D-01 alone |

**No dev readout, and the reason is a measured one.** The dev row is `flexDirection: 'row'` with
`gap: 8` and **no `flexWrap`**, rendered into an absolutely-positioned slot with `right: padR` and
no `left` (`GameScreen.tsx` `devSwitchSlot`) — so it is sized to its content and any excess extends
past the **left** screen edge. At the 12px dev label size the five existing controls already
compute to ≈394px of content, which exceeds a 375pt-wide viewport **today, before this phase**.
Adding `Daily` costs ≈69px more. Placing it right of `Endless` means the phase's own control is not
among the ones that clip; adding a readout as well would spend another ≈30px for a number the Daily
Result panel already shows.

**Recommended, not required** (dev ergonomics only, no production surface): add
`flexWrap: 'wrap'` and `justifyContent: 'flex-end'` to `styles.devRow`, add `left: padL` to
`styles.devSwitchSlot` so the row has a width to wrap within, and add `pointerEvents="box-none"` to
the `devRow` `View` so the now-full-width row does not swallow playfield taps. Phase 14 deletes the
row regardless.
