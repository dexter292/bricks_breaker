Body: first, `if (world.combo > stats.bestCombo) stats.bestCombo = world.combo;` (unconditional,
before the early-return — Pitfall: do NOT gate this behind `evCount > 0`, `world.combo` updates
independently of the event ring). Then `const n = world.evCount; if (n <= 0) return;`. Copy the
`(world.evHead - n + world.evCap) % world.evCap` ring-walk from `src/vfx/consumeEvents.ts` lines
57-90 verbatim. Inside the loop, declare two LOCAL (not struct-persisted) working variables before
the loop starts: `let substepBreakCount = 0;` and `let substepHasExplosiveBreak = false;` — these
reset to fresh values on every call (a substep boundary), which is correct because
`explodeAtCell`'s recursive chain resolves entirely within one `stepWorld` call (one substep) per
research — cascades never span multiple `reduceRunTelemetry` calls.

**Locked cascade-attribution decision:** use the substep-level heuristic (RESEARCH.md Pitfall 1,
option 2), NOT the grid-adjacency algorithm (option 1). Rationale to preserve in a code comment:
grid-adjacency needs local scratch arrays for connected-component grouping inside a worklet,
adding allocation and complexity to the hot path for a highlight/bragging stat, not a
balance-critical number; the substep heuristic is zero-alloc and only risks *overcounting* in the
rare case where two independent, non-chained explosions resolve in the same 8.3ms substep with
multiball active — it can never undercount, and undercounting (not overcounting) is the failure
mode that would actually mislead a player.

For each event in the ring-walk switch on `code`:
- `EventCode.BRICK_BREAK`: `stats.bricksBroken += 1; substepBreakCount += 1;` then read
  `const brickIndex = world.evB[idx]; const flags = brickIndex >= 0 && brickIndex < world.brickCount ? world.brickFlags[brickIndex] : 0; if ((flags & BrickFlags.EXPLOSIVE) !== 0) substepHasExplosiveBreak = true;`
- `EventCode.POWERUP_CATCH`: `const type = world.evA[idx];` then an if/else-if chain comparing
  `type` against `PickupType.MULTIBALL` / `.EXPAND` / `.EXTRA_LIFE` / `.SLOW` / `.FIREBALL`,
  incrementing the matching field.
- `EventCode.LIFE_LOST`: `stats.livesLost += 1; stats.rallyCurrent = 0;`
- `EventCode.PADDLE_HIT`: `stats.rallyCurrent += 1; if (stats.rallyCurrent > stats.longestRally) stats.longestRally = stats.rallyCurrent;`

After the loop: `if (substepHasExplosiveBreak && substepBreakCount > stats.largestCascade) { stats.largestCascade = substepBreakCount; }`.

Do not add a `ticksPlayed` field or any wall-clock field to `RunStats` — per RESEARCH.md Pitfall
2, `world.tick` is already authoritative and is read directly by the app layer in Plan 04; adding
a mirror field here would be a second, driftable counter.
